# 모듈 지도: 데이터 · 프롬프트 · 파이프라인

이 파일의 줄은 [AGENTS.md](../../AGENTS.md) 의 '문서 줄 규칙'을 따른다.

### `canon/autorun.py`

- 자동 집필
- `wanted(name)`: 도는 실행에 받아 둔 일시정지 · 중지 요청. 웹 `AutoView.want` 로 보내 화면이 지금 단계가 끝날 때까지 '멈추는 중'을 보인다
- 다른 프로세스가 쥔 실행이면 `wanted` 는 주인이 아직 읽지 않은 `autorun.want` 를 돌려준다. 주인이 읽어 지우면 빈 값으로 돌아간다
- 목표 화까지 (스토리보드 `_board`, `Policy.storyboard` · `stop_on_board_warnings`) → (큐 시트 `_cues`, `Policy.cue_sheet`) → write → (서술 다듬기 `_polish`, `Policy.polish`, 다듬을 화 `Run.polish_due`) → check + state → 정책(`Policy`) 통과 시 반영을 반복
- 낡은 AI 큐 시트를 다시 받았는데 비어 오면 그 화는 낡은 시트를 넣지 않고 쓰고 `CueSheet.skipped` 로 적는다(`Runner.no_cues`)
- 쓰기 재료 조율이면 스토리보드보다 먼저 조율 메모를 만든다(`_coord`, `coord.remake`, board 단계). 스토리보드도 그 메모를 플롯으로 본다. 사건 수가 달라 받지 못하면 경고만 남기고 원래 플롯으로 쓴다(`Runner.no_coord`)
- 쓰기(`_write`)와 다듬기(`_polish`)는 본문을 넣는 `_edit` 안에서 보낸 프롬프트 기록을 남긴다(`sent.keep`). 다듬은 글을 버리면 기록도 남기지 않는다
- 쓰기 · 다듬기는 손으로 쓸 때와 같이 작품이 켠 고침 규칙을 건다. 쓰기는 `write_episode(ruled=)`, 다듬기는 `pipeline.apply_rules` 로 `polish_episode` 결과를 감싼다
- 자동 집필이 건 규칙 걸기 기록은 kind 를 `auto` 로 남긴다(`_auto`). 쓰기는 `put` 에서 `ep.rule_runs` 에, 다듬기는 `replace_text(rule_runs=)` 로 넣는다
- 정규식 경고 규칙 지적(`origin = "regex"`)은 멈춤 규칙(`Policy.max_issues` 등)에 세지 않는다(`findings.counted`)
- 자동 집필의 쓰기(`_write`)는 `write_episode` 에 `on_chunk` 를 넘기지 않는다. 흘려 받지 않고 지금처럼 다 끝난 본문을 반영한다
- `_cues` 는 같은 실행의 `_board` 가 방금 만든 스토리보드(`Runner.board_lead`: 화 · made_at · 요청 글)면 그 요청 글로 시작하는 큐 시트 요청을 보낸다(`pipeline.cue_lead`)
- 스토리보드 · 큐 시트는 `board` 단계 모델로 부르고 배치로 보내지 않는다. 비용 추정 `calls` 의 키도 `board` 다
- 옛 실행 로그의 스토리보드 단계 `plan` 은 `_measured` 가 `board` 로 읽는다
- 관계 정책(`max_shift` · `stop_on_stage`)은 작품 복사본에 `features.hold` 로 뺀 변경안을 반영해 본다(`review_reasons`)
- 그래서 관계 정책은 실제 반영(`put`)과 같은 제안만 센다
- 변경안 경고 멈춤(`Policy.stop_on_warnings`)은 누락 검사의 '[누락 의심]' 경고를 세지 않는다. 그 경고는 `Policy.stop_on_audit`(기본 꺼짐)가 따로 본다
- 비용 · 시간 추정(`estimate`)은 누락 검사를 켠 작품에서 상태 변경안 호출을 화마다 하나 더 센다(상태 변경안 단계 값으로 어림)
- 이야기 데이터 정책은 `_story_reasons` 가 본다. 모두 기본으로 꺼져 있어(0 · false) 켜기 전과 같이 돈다
- 새 인물 멈춤(`Policy.stop_on_new_characters`, `StateDelta.new_characters`)
- 새 비밀 멈춤(`Policy.stop_on_secrets`, `StateDelta.secrets_added`)
- 새 인물 · 새 비밀 멈춤은 반영(`pipeline.apply_delta`)이 빼는 항목을 세지 않는다: 이미 있는 인물 id, 이미 있거나 겹친 비밀 id, 설정에 없는 인물의 비밀
- 복선 회수 멈춤(`Policy.stop_on_resolve`): 작품에 열려 있는 복선만 센다
- 이르거나 큰 복선 회수 멈춤(`Policy.stop_on_early_resolve`): 이번 화가 `due_ep` 보다 앞이거나 `scope` 가 part · series 인 복선
- 기한 닫힘 멈춤(`Policy.stop_on_deadline_done`): 작품에 열려 있는 기한만 센다
- 시간 건너뜀 멈춤(`Policy.max_time_jump_days`, 0 이면 끔): `timeline.current_day` 에서 `StateDelta.time.day` 까지 앞으로 간 날수. 어느 쪽이든 날수를 모르거나 시간 기록을 껐으면 보지 않고, 거슬러 가는 것도 보지 않는다
- 지운 칸 멈춤(`Policy.stop_on_clear`, `CharacterState.cleared`). 칸 이름은 `CLEAR_NAMES` 로 상태 승인 화면과 같은 말로 적는다
- 상태 변경안의 본문 지문(`StateDelta.basis`)이 지금 본문과 다르면 검토 대기로 두지도 반영하지도 않고 `paused` · `changed` 로 멈춘다(`_same_text`)
- 본문이 출력 길이 한도에 걸려 끊기면(`pipeline.WriteCut`) 그 화를 반영하지 않고 `paused` · `cut` 으로 멈춘다. 이어 가면 그 화 본문을 다시 쓴다
- 이어 가며 다시 쓰기(`back`)는 지난 본문을 이전 판(`TextVersion`)으로 남기며 `meta_cut` · `rule_runs` 도 그 판으로 옮기고 화에서 비운다
- 배치(`llm.BatchLLM`) 켜고 끄기
- 배치를 취소하지 못하면 배치 이름을 서버 로그(`canon` 로거)에 경고로 남긴다(`_cancel_batches`)
- 기다리는 배치마다 보낸 프롬프트 지문을 `Run.batch_keys` 에 남긴다. 이어 갈 때 다르면 `BatchLLM` 이 그 배치를 취소하고 다시 보낸다(일시정지 중 본문 · 플롯을 고친 경우)
- 오류로 멈추면 호출 경로를 서버 로그에 남긴다
- 오류로 멈춘 이유 칸은 `llm.explain_error` 의 원인과 할 일이다
- 하루 한도 · 선불 크레딧 소진(`llm.QuotaSpent`)이면 기다리지 않고 `paused` · `quota` 로 멈춘다. 한도가 풀리거나 충전한 뒤 이어 간다
- 비용·시간 추정
- 실행 중 토큰 · 비용(`Run.tokens_in` · `cost`)은 `Runner._call` 이 `usage.collect()` 로 모은 단계 안의 모든 호출을 더한다(형식 고치기 재시도, 검수의 여러 호출, 다른 스레드의 동작 검사)
- 실행 중 비용은 `usage.totals` 로 사용량 화면과 같은 값(캐시 · 배치 요금)이다. 기록하지 않는 LLM(mock)은 마지막 호출의 `last_usage` 로 짐작한다
- 로그 줄(`LogEntry`)의 `tokens_out` 은 단계 안 호출의 합이고 `calls` 에 호출 수를 남긴다. 옛 기록은 호출 하나로 읽는다
- 비용 · 시간 추정(`_measured`)은 지난 로그의 출력 토큰을 호출 수로 나눠 호출 하나의 평균으로 쓴다
- 추정의 입력 · 출력 토큰은 단계 백엔드 · 모델의 글자 → 토큰 직선(`usage.stage_rate`)으로 센다
- 추정 결과의 `token_rates` 는 단계마다 쓴 기울기 · 붙는 토큰 · 출처(default · measured · fallback)다
- 정착 문체 흐름 멈춤(`Policy.max_style_distance`, 0 이면 끔, `anchor.rolling`)
- `autorun.json` 에 진행 기록
- 변경안 반영(`_review` 의 put)은 반영 전제 `pipeline.check_applicable` 에 걸리면 반영하지 않고 paused 로 멈춘다
- 검토 대기의 그대로 반영(`resume` 의 take)도 `check_applicable` 에 걸리면 반영하지 않고 오류를 낸다
- 자동 반영(`_review` 의 put)과 그대로 반영(take)이 끝나면 pending.json 의 그 화 상태 변경안(`state:<화>`)을 지운다(`_drop_pending_state`)
- 서버 재시작 후 이어 가기
- 도는 실행은 작품 폴더의 `.autorun.lock` 에 flock 을 쥔다(`_take`, `Control.owner`). 프로세스가 죽으면 OS 가 푼다
- 다른 프로세스(명령줄 `canon auto` 나 다른 서버)가 잠금을 쥐면 `elsewhere` 가 참이고 `active` 도 참이다(화면 저장 보호가 켜진다)
- 그동안 `start` · `resume` · `set_batch` · `set_policy` 는 `ELSEWHERE` 로 거절하고, `resume_all` 은 그 작품을 건너뛴다
- 같은 프로세스의 다른 스레드가 시작 · 이어 가기를 준비하는 중(`_taking` 이나 `Control.owner` 가 있고 러너는 아직 없음)이면 `_control` 은 잠금 파일을 보기 전에 `STARTING` 으로 거절한다
- `_control` 이 잠금 파일을 잡았지만 `Control` 을 아직 등록하지 않은 동안에도 `elsewhere` 는 `_taking` 을 보고 거짓을 돌려준다(이 프로세스의 실행을 다른 곳으로 보지 않는다)
- `_take` 의 flock 재시도 대기는 전역 `_lock` 밖에서 한다. 다른 작품의 요청을 막지 않는다
- 그동안 `request` 는 상태를 쓰거나 배치를 취소하지 않고 `autorun.want` 에 요청만 남긴다(중지를 일시정지로 낮추지 않는다)
- `autorun.json` 과 `autorun.want` 는 `store.write_atomic` 으로 쓴다. 임시 파일 이름에 pid 와 스레드 id 가 들어가 주인의 기록과 다른 요청이 서로 겹치지 않는다
- 러너는 `_checkpoint` 와 배치 대기(`Control.wait`)에서 `autorun.want` 를 읽는다(`Control.poll_want`). 주인이 된 실행은 남은 요청을 버린다
- `get_run` · `set_batch` · `set_policy` · `renumber` 는 이 프로세스의 실행이 끝났으면 메모리 값 대신 `autorun.json` 을 읽고 쓴다(다른 프로세스가 그 뒤에 이어 간 기록을 덮지 않게)
- 화를 반영할 때마다 작업의 `step_ep` 를 그 화로 고친다(화면 알림 `notify.js`)
- 반영에서 뺀 항목(`pipeline.apply_delta` 가 돌려준 것)은 화마다 경고 기록으로 남긴다. 검토 화면 없이 승인한 반영도 같다
- 화면은 `static/auto.js`

### `canon/board.py`

- 화별 스토리보드 계산
- 켜짐(`on`)
- 직전 화 원문(`prev_text`)
- 만든 입력의 지문(`basis`) · 낡음(`stale`, 본문을 쓰기 전에만)
- 날수 · 요일(`days`, `weekday`: 작품 기준이 없으면 직전 화 기록 글의 요일에서)
- 시간 한 줄(`time_line`)
- 기한 줄(`deadline_rows`)은 예산 인자를 받는다. 쓰기 요청의 스토리보드 블록만 작품 예산(`context.budget`)을 넘긴다
- `deadline_rows(trace=)` 는 예산으로 뺀 기한을 보기의 'board' 블록에 적는다
- 쓰기 재료 꼭 쓸 것만(`lean`)과 그때 쓰기 요청에 남기는 이어받을 것의 종류(`LEAN_HANDOVER`)
- 고정점만(`fixed_only`)은 쓰기 재료 조율(`coord`)에서도 참이다
- 중심 장면 번호(`focus`, 장면 수 밖이면 0)
- 상태창 단계마다 바뀌기 전 · 뒤 값(`steps`, `statwin.resolve`) · 창 글(`window_text`)
- Canon 경고(`checks`: 맡은 장면 없는 사건 · 모르는 id · 값 범위 · 관계 단계를 두 칸 넘게 옮기는 플롯 `pace.plot_warnings`)
- 자동 집필 멈춤 이유(`stop_reasons`, `STOP_KINDS`)
- 화면 값(`view`)
- LLM 호출 없음
- AI 호출은 `pipeline.make_storyboard`, 작가 요청대로 고치기는 `pipeline.revise_storyboard`
- 두 호출 모두 `pipeline._board_draft` 안에서 출력을 `out_cap(BOARD_OUT_TOKENS)`(16,384토큰)로 막는다
- 화면은 `static/board.js`

### `canon/cancel.py`

- 웹 작업 멈추기 신호
- `notice` · `say`: 작업 진행 줄에 잠깐 띄울 글. `jobs.start` 가 `Job.retry` 에 쓰게 둔다
- `jobs.start` 가 스레드마다 둔다
- LLM 호출 전과 저장 전에 `check()` 로 확인해 멈춘 작업이 결과를 저장하지 못하게 한다
- 멈춘 뒤 온 응답을 남기는 곳은 `ignored()` 안에서 저장한다(스토리보드 `_keep_late_board`)

### `canon/cli.py`

- 명령줄 (`python -m canon ...`)
- `import` 는 웹 본문 저장과 같은 규칙을 따른다: 초안 화는 거절하고, 확정 화는 앞 화가 모두 반영돼야 넣는다(`pipeline.require_previous`)
- `import` 는 받은 본문에 작품이 켠 고침 규칙을 건다(kind import, `pipeline.apply_rules`). 웹의 받은 본문 붙여 넣기(`Text.source = "import"`)와 같다
- `write` · `import` · `rewrite` 는 고친 곳 수를 '규칙으로 N곳 고쳤어요' 로, 시간 한도로 건너뛴 묶음을 '! 규칙 묶음 ○○을 거는 데 너무 오래 걸려서 건너뛰었어요' 로 찍는다(`_print_rules`)
- `fix` 는 `revise_passage(rules=True)` 로 후보마다 규칙을 걸고 후보 머리에 고친 곳 수를 붙인다. `rework` 는 제안의 `ruled` 를 `accept_rework` 에 넘긴다
- 전체 명령 목록은 `python -m canon --help`
- 해석기는 `build_parser` 가 만들고, 명령은 갈래 함수(`_plan_commands` · `_write_commands` · `_tool_commands` · `_app_commands` · `_data_commands` · `_lab_commands`)가 더한다. 새 명령은 맞는 갈래 함수에 넣는다
- 단편 흐름: `new` → `style` → `arc` → `plot` → (사용자 수정) → `confirm` → (스토리보드 → 큐 시트, 웹 집필 화면 · 자동 집필) → `write` → `check` → `update` 반복
- `run` 이 쓰기 · 검수 · 반영을 자동으로 되풀이한다
- `update -y` 의 관계 미리 보기는 반영처럼 `features.hold` 로 뺀 제안을 빼고 계산한다(`_print_relation_preview`)
- `update` 는 반영 전제(`pipeline.check_applicable`)에 걸리면 변경안을 만들지 않고 까닭을 알린다. 반영 완료한 화는 앞 화로 되돌리는 `revert <작품> <n-1>` 을 알려 준다
- `update`(`-y` 없이)는 관계 미리 보기 전에 관계 단계와 반대인 관계 바뀜(`StateDelta.rel_flagged`)을 따로 보여 주고 묻는다. 기본은 빼고, 뺀 것은 `d.dismissed` 에 남긴다(`_ask_flagged`)
- `update`(`-y` 없이)는 이미 있는 확정 사실과 비슷한 새 사실(`StateDelta.fact_near`)도 옛 사실과 나란히 보여 주고 묻는다. 기본은 빼고 `d.dismissed` 에 남긴다(`_ask_near_facts`)
- `update -y` 는 비슷한 새 사실을 반영하지 않고 빼 둔 수를 알린다(`features.hold`)
- 장편(`new --serial`)은 `arc` 대신 `series` 를 한 번 부른다
- 장편은 아크마다 `nextarc` → `plot` → `confirm` → `run` → `recap` 을 되풀이한다
- `auto --stop` 은 다른 곳(웹 서버)에서 도는 실행이면 중지를 청했다고 알린다(`autorun.elsewhere`)
- 명령별 쓰임
  - `abilities`: 스킬 · 특성 도감(설명 · 효과 · 대가, 가진 인물과 얻은 화) 보기
  - `arcs`: 장편 진행 보기
  - `backups`: 백업 목록 보기 · `--restore` 로 그 판으로 되돌리기(지금 판은 먼저 백업으로 남김)
  - `branch`: 반영까지 끝난 전개를 지우지 않고 n화부터 다른 전개를 쓰는 갈래(원본은 그대로)
  - `branch-compare`: 갈래 비교
  - `branches`: 갈래 보기
  - `cast`: 인물별 등장 · 지금 관계 · 화별 타임라인(바뀐 설정 포함) 보기

### `canon/context.py`

- 장편 프롬프트 크기 관리
- 블록 재기(`blocks`, 사용량 기록 · 연구 화면)
- 블록 글자 예산(`BUDGET`)
- 쓰기 가족 예산 키 `WRITE_KEYS`: 작품 설정(`Settings.budgets`)으로 바꿀 수 있는 키는 이 14개뿐이다
- 작품 예산 `budget(p, key)`: 장편이고 `WRITE_KEYS` 의 키에 작품 값이 있으면 그 값, 아니면 `BUDGET[key]`. 단편은 늘 기본값
- 저장한 값이 `budget_ok` 를 지나지 못하면(손으로 고친 `project.json` 등) `budget` 은 그 값을 무시하고 `BUDGET[key]` 를 쓴다
- 작품 예산 범위 `budget_range(key)`: 기본값의 1/4 ~ 4배를 100 단위로 내림, 가장 작은 값은 100
- 작품 예산 검사 `budget_ok(key, value)`: `WRITE_KEYS` 의 키 · 100 단위 · 범위 안. 0 은 받지 않는다(빼려면 블록을 끈다)
- 넣은 이유 · 뺀 이유 이름은 상수 `REASON_*` · `DROP_*` 한 곳에 둔다(보기와 컨텍스트 활성화가 같은 말을 쓴다)
- 보기 기록 `Trace`: `item(블록 id, 이름, 이유)` · `drop(…)`, `items` · `dropped` 는 블록 id → [(이름, 이유)]
- `Trace.forget(블록 id)` 는 꺼진 블록의 항목을 지운다(`prompts.follow_parts` 가 부른다)
- 뺀 줄 이름 `trace_label`(앞 '- ' 를 떼고 `TRACE_LABEL` 40자까지)과 뺀 줄 적기 `trace_drops(trace, 블록 id, 줄들)`. 예산으로 줄을 빼는 함수들이 함께 쓴다
- 무관한 옛 사실은 하나하나 적지 않고 `trace_unrelated` 가 '옛 사실 N개' 한 줄로 적는다. 예산으로 뺀 사실은 이름으로 적는다
- 복선의 넣은 이유는 `foreshadow_reason`(`FORESHADOW_REASONS`: 순위 0~2 '아크 회수 · 기한', 3~4 '작품 · 부 단위', 5~6 '최근')
- `pick_facts` · `pick_knows` · `fit_cast` · `fit_named` 는 선택 인자 `trace` 를 받아 넣은 항목과 뺀 항목을 적는다. `None` 이면 지금과 같은 일을 하고 같은 값을 돌려준다
- 숨긴 비밀의 보기 기록은 `pick_secrets` 가 아니라 `trace_secrets(trace, 후보, 고른 것, 인물)` 이 한다. 상태 예산으로 인물을 뺀 뒤 요청에 찍히는 비밀만 적는다
- `trace_secrets` 는 `dynamics.describe_relations` 와 같은 규칙(주인이 인물에 있고 모르는 인물 하나 이상이 인물에 있음)을 쓴다
- 관련 사실(`pick_facts`) · 비밀(`pick_secrets`) · 떡밥(`rank_foreshadows`) · 인물이 아는 정보(`pick_knows`, 뺀 수는 `prompts.knows_note`) 고르기
- 확정 사실이 들어온 화(`facts_learned`): 반영 기록의 `new_facts` 로 센다. 고친 화 다시 맞추기 · 빼 둔 사실 넣기도 그 기록에 더해 잡힌다. 저장하지 않는다
- `facts_learned` 에 인과율 `apply_impact` 로 넣은 사실은 없다(반영 기록을 남기지 않음). 설정 단계 · 직접 적은 사실도 없다
- 비슷한 확정 사실(`near_fact`): 새 사실의 한글 3글자 조각 가운데 `FACT_NEAR`(0.5) 이상이 한 옛 사실과 겹치면 그 옛 사실. 조각이 `FACT_NEAR_MIN`(3)보다 적으면 보지 않는다
- 기획 프롬프트 인물(`planning_cast`)
- 인물 이름(`names_of`: 세 글자 이름은 성을 뗀 이름도, `metrics.name_forms`)
- 이름으로 켜는 인물(`named_ids` · `name_pattern`, 남은 예산 `fit_named`) · 마지막으로 나온 화(`last_seen`)
- 검수용 옛 본문 단락 찾기(`recall`, 질문 여러 개는 색인 `PassageIndex` 하나로, 검수 넓히기도 이 색인)

- 진술과 겹치는 줄 · 사실(`related_lines` · `related_facts`, 셈이 있는 진술은 셈이 있는 줄을 앞세움 `has_count`)
- LLM 호출 없음
- 단편 경로는 쓰지 않는다

- 정리(`CLEAN`) · 반영(`APPLY_FIRST` 새 인물 직후, `APPLY_LAST` 기록 전) · 되돌리기(`REVERT_FIRST` 스냅샷으로 덮기 전, `REVERT_LAST` 뒤) 목록
- `pipeline.clean_delta` · `apply_delta` · `revert` 가 목록을 차례로 부른다
- 정리 훅은 한 인물에 대한 경고를 (글, 인물 id) 로 돌려준다(`Warn`)
- `_new_cast_known` 은 새 인물에 온 이미 있는 인물 id 를 그 인물 경고로 알린다(반영은 새로 더하지 않음)
- `clean` 이 그 id 를 `StateDelta.warn_to` 의 같은 차례에 넣는다
- 글만 돌려준 경고, 훅이 `d.warnings` 에 바로 붙인 경고, AI 경고는 대상이 "" 다
- `align_warn_to` 가 `warn_to` 길이를 `warnings` 에 맞춘다
- 사람 검토 없이 반영할 때(자동 집필 · `run -y` · 플레이)는 `hold`(`HOLD`)가 작가가 골라야 하는 제안을 빼서 남겨 둔다. 관계 단계와 반대인 유형 바뀜(`pace.hold`)은 남기지 않고 빼서 경고에 적는다
- 정리 훅 `_near_facts` 는 이미 있는 확정 사실과 비슷한 새 사실을 `StateDelta.fact_near`(새 사실, 옛 사실)에 적는다. 경고는 내지 않는다
- `_near_facts` · `_hold_near_facts` 는 장편만 본다. 단편은 표시도 빼기도 하지 않는다
- 정리 훅 `_untag_facts` 는 새 사실이 따라 적은 '(n화)' 표시(`context.FACT_TAG`)를 뗀다. 비슷한 사실 보기 전에 돈다. 장편만 본다
- HOLD 훅 `_hold_near_facts` 는 그 새 사실을 `d.dismissed.new_facts` 로 옮기고 경고에 적는다. 작가는 반영 기록에서 나중에 넣는다(`pipeline.take_dismissed_fact`)
- 상태를 가진 기능을 더할 때는 `pipeline.py` 를 고치지 않고 기능 모듈에 훅을 두고 이 목록에 넣는다(목록 순서가 부르는 순서)
- LLM 호출 없음

### `canon/findings.py`

- 검수 세션
- 회차(`Episode.rounds`, `CheckRound`: 새로 · 다시 · 사라진 지적 id)마다 검수 결과를 지적 목록(`Episode.findings`)에 합친다(`merge`, `pipeline.apply_check` 가 부름)
- 지적 `Finding`: 상태 open · fixed · kept · wrong, 메모, 심각도 crit · mid · low, 처리 기록 `log`
- 같은 문장(`same_quote`)이면 이어 붙이고 kept · wrong 과 작가가 정한 심각도는 지키며 fixed 가 다시 나오면 연다
- 문장이 본문에 있는지(`in_text`)는 띄어쓰기 · 따옴표 · 문장 부호를 빼고 본다(`foreshadows.found`)
- 그래서 따옴표 모양만 바꿔 옮긴 지적을 '문장이 사라졌다'며 고침으로 닫지 않는다
- 열린 지적(`open_findings`)
- 검수가 끝났는지(`check_done`, `home.js` `checkState` 의 done 과 같은 규칙, 작품 목록 `open_checked`)
- 자동 집필이 세는 지적(`counted`, 사소 빼기)
- `counted` 는 정규식 경고 규칙 지적을 세지 않는다(자동 집필 멈춤 · 검토 이유)
- 작가가 정하기(`set_status` · `set_severity`, 웹 `set_finding`, 명령줄 `check --keep` · `--sev`)
- 웹 `set_findings`(`PUT …/findings`)는 열린 지적 여러 개를 한꺼번에 kept · wrong 으로 정한다. 없는 id · 열리지 않은 지적이 섞이면 아무것도 바꾸지 않는다
- 명령줄 `check --recheck-fixed` 는 고친 곳만 다시 보기(`pipeline.recheck_fixed`)
- 고침안이 건드리는 다른 지적(`touches`)
- 지적 하나 다시 검수 결과 넣기(`settle`: 고침으로 닫기, 딸린 지적 `add_children`)
- 마지막 검수 뒤 되돌리지 않은 수정(`edits_since_check`, `check_done` 과 같은 셈)
- 고친 곳만 다시 볼 지적(`fix_recheck_targets`): 마지막 검수 뒤 고침안 묶음(source fix)을 넣은 열린 지적들
- 직접 고친 곳이나 다른 AI 수정이 함께 있어도 고침안을 넣은 지적은 `fix_recheck_targets` 대상이다. 그 수정은 다시 검수가 바뀐 문단에서 본다
- 다시 검수 거르기(`scoped`): 바뀐 문단(`pipeline.check_scope`) 밖에서 새로 나온 지적은 넣지 않는다. 옛 지적과 같은 문장 · 치명 · 인용 없는 지적은 넣는다
- `pipeline.apply_check` 가 `scoped` 를 부르고 회차에 `CheckRound.scoped` · `outside`(넣지 않은 수)를 남긴다. `Episode.issues` 는 넣은 지적만
- 묶음을 넣은 뒤 이미 다시 본(기록 `recheck`) 지적은 `fix_recheck_targets` 에서 뺀다. `home.js` `fixRecheckTargets` 와 같은 셈
- 새 판(`new_version`: 결정한 지적만 남김)
- 세션 비우기(`clear`)
- 합치기는 출처(`ConsistencyIssue.origin`: ai · rule)가 같은 지적끼리
- 정규식 경고 규칙 지적(`origin = "regex"`)은 같은 규칙(`regex_rule`)끼리만 잇는다(`_match`). 한 문장에 두 규칙이 걸려도 결정이 섞이지 않는다
- 규칙 지적의 다시 검수는 `pipeline.recheck_finding` 이 LLM 없이 판정만
- 정규식 경고 지적의 다시 검수도 LLM 없이 그 규칙만 지금 본문에 다시 걸어(`regexrules.hits(only=)`) 같은 문장에 걸리는지 본다
- 고침안 · 다시 검수의 AI 호출은 `pipeline.propose_fixes` · `apply_fix` · `undo_fix` · `recheck_finding`
- 고침안 한꺼번에: 받을 지적 `pipeline.fix_targets`(넣을 수 있는 안 `fix_usable` 이 없는 열린 지적, `check.js` `fbNeed` 와 같은 셈), 웹 작업 `fixes`(`FIX_WORKERS` 개씩 동시에, 받는 대로 `store_fixes`), 고른 안 넣기 `apply_fixes`(웹 `POST …/fixes/apply`, 못 넣은 것은 까닭과 함께)
- 웹 작업 `fixes` 는 지적을 `FIX_BATCH`(8)개씩 묶어 `pipeline.propose_fixes_batch` 로 한 번에 묻는다(LLM `FixBatch` → `FixItem`, 지적 id 로 맞춤)
- 묶음 답에서 빠진 지적만 `propose_fixes` 로 하나씩 다시 묻는다. 고침안도 답도 빈 항목은 빠진 것으로 본다
- 묶음 호출 자체가 실패하면(거절 · 시간 초과 · 형식 오류) 그 묶음의 지적을 `propose_fixes` 로 하나씩 다시 묻는다. 지적 하나뿐인 묶음은 다시 묻지 않고 실패에 싣는다
- 묶음 답의 지적마다 `clean_fixes` 를 거친다(`_fix_result`, 한 지적 고침안과 같은 셈). 요청에 없는 id 와 겹친 id 는 버린다
- 프롬프트 `prompts.fix_prompt` · `recheck_prompt`(앞부분은 검수와 같은 `check_material`)
- 고친 곳만 다시 보기: `pipeline.recheck_fixed` 가 대상 지적을 한 번의 호출(LLM `FixRecheckReport`, 단계 check)로 다시 묻고 `apply_fix_recheck` 가 지적마다 `settle` 한다. 회차는 늘지 않는다
- 고친 곳 둘레(`fix_around`)에는 직접 고친 곳을 포함한 검수 뒤 수정이 모두 들어간다
- 고친 곳만 다시 보기 프롬프트 `prompts.fix_recheck_prompt` 는 검수 자료 전체 대신 `static_context`(검수와 같은 앞부분)와 고친 곳 둘레 문단(`fix_around`, 앞뒤 `FIX_AROUND` 문단)만 넣는다
- `recheck_fixed` 는 `static_context` 길이를 캐시 경계(`llm.PREFIX_HINT`)로 넘긴다. 고친 뒤라 본문이 달라 검수 자료의 캐시는 읽지 못한다
- `recheck_fixed` 는 묻지 않은 id 와 같은 id 의 두 번째 답을 버린다. 규칙 지적은 LLM 없이 `recheck_finding` 으로 판정만
- 고친 곳 둘레(`_fix_spots`)는 고친 글이 본문에 여러 번 나오면 기록한 자리(`TextEdit.start`)에 가장 가까운 곳을 고른다
- 웹 작업 `recheck` 는 묻기 전 상태(`fix_recheck_basis`: 검수 시각 · 본문 · 지적별 묶음)를 남긴다. 그사이 검수나 되돌리기로 바뀌었으면 `apply_fix_recheck` 가 아무것도 넣지 않고 오류로 끝낸다
- 묶음이 바뀌었거나 그사이 닫힌 지적은 건너뛴다. 작업 결과의 풀림 · 아직 어긋남 수는 실제로 넣은 결과만 센다
- 묶음 프롬프트 `prompts.fix_batch_prompt`: 검수 자료, id 를 단 지적 목록, 결정한 문장, 규칙 한 번, 요청은 맨 뒤
- 고침안(한 지적 · 묶음) · 다시 검수는 `check_material` 의 본문 바로 앞(`prompts.check_cache_cut`)을 캐시 경계(`llm.PREFIX_HINT`)로 넘긴다. 세 프롬프트 함수는 미리 만든 자료를 `material` 로 받는다
- 검수(`check_episode`)도 같은 자리(`check_cache_cut`)를 캐시 경계로 넘긴다. `check_prompt(material=)` 가 미리 만든 자료를 받는다
- 경계를 본문 앞에 두는 까닭: 본문 끝에 두면 고침안이나 작가가 본문을 고칠 때마다 앞부분 캐시를 통째로 버렸다(2026-11-09, 상태 변경안 35번 중 17번). 본문 블록은 `check_material` 의 맨 끝이다
- 상태 변경안(`extract_state`)은 백엔드가 `family_cache` 면 `state_prompt(head=check_material)` 로 검수 자료로 시작하고 `check_cache_cut` 을 캐시 경계로 넘긴다. 다른 백엔드는 예전 프롬프트다
- 작품 설정 `Settings.state_audit`(기본 꺼짐)를 켜면 `extract_state` 가 정리한 변경안을 `audit_delta` 로 한 번 더 본다(`audit` 단계 모델, 인자 `audit` 로 바꿀 수 있음)
- `audit_delta` 는 n화 본문과 변경안 줄임(`prompts.audit_prompt`)을 넣고 `AuditReport` 를 받는다. 종류는 비밀 공개 · 관계 사건 · 약속 · 부상 · 정체 공개 · 장소 이동 · 소지품
- `audit_delta` 는 본문에서 찾을 수 없는 인용(`findings.in_text`)을 버리고 `AUDIT_MAX`(6)개까지 '[누락 의심]'(`AUDIT_MARK`) 경고로만 붙인다. `warn_to` 는 "" 로 차례를 맞춘다
- `audit_delta` 는 변경안 칸을 바꾸지 않고, 실패하면 경고 없이 넘어간다. 반영 기록에서 돌아온 변경안(`carried_delta`)은 다시 보지 않는다
- 띄어쓰기 · 문장 부호를 뺀 인용이 `AUDIT_QUOTE_MIN`(8)자보다 짧으면 버린다
- 다시 쓰는 변경안(`carried_delta`, 반영 취소 `web._revert_kept`)은 옛 '[누락 의심]' 경고를 뺀다(`drop_audit_warnings`)
- 배치 자동 집필에서도 누락 검사는 실시간 호출이다(상태 변경안만 배치). 사용량에는 그대로 잡힌다
- 작업지시서(`brief`, 채팅 앱) 경로에는 누락 검사가 없다
- 결정은 검수 프롬프트에 넣지 않는다
- LLM 호출 없음

### `canon/jobs.py`

- 웹의 오래 걸리는 AI 작업을 스레드로 돌리는 메모리 작업 목록
- `Job.retry`: AI 호출이 기다리거나 다시 부르는 중인 사정(`cancel.say` → `Job.say`). 스레드마다 `retries` 에 두고 남은 하나를 보인다. `public()` 에 싣는다
- `Job.step_wait`: 대화 에이전트 한 단계의 AI 호출 한도(초, `agent.step_wait`). `public()` 에 싣는다. 0 이면 화면이 기본값을 쓴다
- `Job.partial`: 흘려 받는 중인 AI 글(지금까지 받은 글 전체). 저장한 글이 아니다. 도는 작업만 `public()` 에 싣는다
- `Job.set_partial(text)` 는 잠금(`_lock`) 아래에서 고친다. 끝나거나 멈춘 작업은 받지 않아 늦게 온 조각이 부분 글을 되살리지 않는다
- 작업이 끝나거나 멈추거나 실패하면(`run` 의 finally, `stop`) 부분 글을 비운다
- 중복 실행 막기
- `Job.target`: 같은 종류를 대상(인물 id, 지적 id)마다 따로 돌린다. 중복 막기는 (작품, 종류, 화, 대상)으로 본다. `public()` 에 싣는다
- 자동 업데이트가 다시 시작하려고 기다리는 동안(`draining`) 새 작업은 `Draining`(400, '서버를 곧 다시 시작해요')으로 거절한다. 자동 집필(`auto`)은 받아서 첫 단계 전에 멈춘다
- `running()` 은 다른 스레드가 작업을 더해도 깨지지 않게 잠금 안에서 센다
- `project_lock(name)` 은 프로세스 안 잠금(재진입하지 않음)을 잡은 뒤 작품 폴더의 `.edit.lock` 에 `fcntl.flock` 을 건다
- `project_lock` 을 거치는 경로끼리만 프로세스가 달라도 서로 덮지 않는다
- `project_lock` 을 거치는 경로: 웹 저장(`web._save` · `put_project` 등), 자동 집필(`autorun._edit`, 명령줄 `run` 포함), 대화 에이전트(`agent._edit`), 큐 시트 실험(`cue.with_lock`), 명령줄 `tofix`
- 명령줄의 다른 명령(`write` · `check` · `update` · `confirm` · `plot` 등)은 아직 잠금 없이 `store.load` → AI 호출 → `store.save` 로 작품 전체를 저장한다
- 명령줄 `write` 는 보낸 프롬프트 기록(`sent.keep`)과 마지막 저장만 `project_lock` 안에서 한다. 읽기와 AI 호출은 잠그지 않는다
- 그래서 그 명령이 도는 동안 웹 서버가 저장한 내용은 아직 덮일 수 있다(2026-11-05 확인, `cli.py` 의 `store.save(` 65곳)
- `project_lock` 은 다른 프로세스가 쥐고 있으면 `LOCK_WAIT`(30초)까지 기다리고, 넘기면 `Locked`(400, '다른 프로그램(명령줄 등)이 이 작품을 고치고 있어요')를 낸다
- `project_lock` 의 flock 은 `store.save` 의 `.lock` 과 다른 파일이라 잠금 안에서 저장해도 막히지 않는다. 점으로 시작하는 열쇠(`revlab.lock_key`)와 폴더가 없는 작품은 프로세스 안에서만 잠근다
- `project_lock` 을 쥐는 구간은 읽고 고쳐 저장하는 짧은 구간이다. AI 호출은 그 밖에서 한다
- 진행률
- 작업이 맡은 화를 저장 덮어쓰기에서 지키기(`owned_episodes`)
- 멈추기(`stop`)
- 실패한 작업의 호출 경로를 서버 로그(`canon` 로거)에 남긴다. 화면에는 오류 문구만 보인다
- 작업 오류 문구(`Job.error`)는 `llm.explain_error` 가 고른다
- 멈췄지만 AI 응답을 기다리는 같은 작업 찾기(`lingering`)
- 끝난 작업은 `KEEP_SECONDS` 뒤 목록에서 뺀다(`_prune`)
- 멈췄지만 아직 응답을 기다리는 작업은 응답이 끝날 때까지 빼지 않는다. 빼면 `lingering` · `waiting_on` 이 못 찾아 호출이 겹친다
- 같은 화의 AI 작업(`EP_AI_KINDS`) 가운데 응답을 기다리는 것 찾기(`waiting_on`). 종류가 달라도 같은 화면 호출이 겹친다
- `EP_AI_KINDS` 에는 고친 곳만 다시 보기 작업 `recheck` 도 든다
- `EP_AI_KINDS` 에는 지적 하나의 고침안 `fix_one` 과 이 지적만 다시 검수 `recheck_one` 도 든다
- 단계 하나가 마지막으로 끝낸 화(`Job.step_ep`). 화면 `notify.js` 가 바뀔 때마다 알린다

### `canon/metatail.py`

- 본문 앞뒤에 섞인 작업 설명(메타 코멘트) 찾기
- 확실한 머리말 · 꼬리 떼기(`split`): 대사 · 대괄호 글을 뺀 서술에 Canon 작업 낱말(`STRONG`: 스타일 프로필 · 플롯 · 본문을 · 요청하신 · 짚어 둘 …)이 있고 존댓말이 반 넘는 앞뒤 문단, 'n화 본문입니다' 머리말, '작가 메모' 머리와 목록, 한글이 거의 없는 영어 메모. 서술이 원래 존댓말인 작품은 작업 낱말 둘 이상
- 응답 전체가 작업 설명 · 거절 · 되묻기인지(`whole`)
- 흔한 말(`SOFT`: 원고 · 다음 화 · 원하시면 …)만 있는 앞뒤 문단은 떼지 않고 경고(`warnings`). 작가물 · 편지 · 시스템 알림 · 이야기꾼의 맺음말을 지키려는 것(2026-10-31 적대적 검토)
- 앞 · 뒤를 나눠 주는 `parts`(되살릴 자리). `split` 은 그 위의 옛 모양
- `pipeline._write` 가 떼고(서버 기록 warning, `cut` 목록을 주면 `MetaCut` 으로 채움) 다시 쓰며(`whole`), `pipeline.style_drift` 가 경고를 붙인다
- LLM 호출 없음

### `canon/opening.py`

- 초반 1~3화: 지표, 흡입력 판정, 여는 방식 여러 안
- 여는 방식 안을 고르거나 되돌려도 그 화의 작가 연출 지시(`Episode.direction`)는 남긴다
- `pipeline.py` 에서 옮긴 구역이다. `pipeline` 맨 끝의 `_attach_split` 이 `EXPORTS` 의 이름을 `pipeline` 에도 둬서 `pipeline.<이름>` 으로 그대로 부른다

### `canon/pipeline.py`

- 장편 전환(`serialize.py`) · 재구성(`reshape.py`) · 초반 1~3화(`opening.py`)는 따로 둔 모듈이다(`SPLIT`). 새 공용 도우미는 이 파일에 두고 그 모듈이 불러 쓴다
- 단계별 로직
- 차례: 설정 제안 → 스타일 분석 → 기승전결 → 화별 플롯 → 스토리보드 → 큐 시트 → 본문 → 검수 → 상태 추출/반영
- 기승전결 `plan_arc` 는 `Settings.heat_plan` 을 켠 단편이면 열 계획을 함께 받는다(응답 `HeatArcPlan`, 요구 `prompts.heat_arc_rules`)
- 열 계획 정리 `clean_heat_plan`: `heatplan.fit` · `fit_turn`, 판돈은 단서 · 빈 것을 빼고 심는 화를 자르고 겹치지 않는 id(`fs-<화>-h<k>`)
- 열 계획 적용 `apply_heat_plan`: 계획 · 원칙 · 뒤집힘을 바꾸고 판돈은 같은 id 가 없을 때만 복선에 더함. 명령줄 `arc` 와 화면 구조 제안 고르기(`heatApply`)가 쓴다
- 열 계획을 받을 범위 `heat_target`(단편 작품 전체, 장편은 아크 번호 또는 다 쓰지 않은 첫 아크)과 받기 `propose_heat`(본문 있는 화는 지금 계획 줄을 지킨다)
- 다음 아크 `plan_next_arc` 는 `heat_plan` 을 켜면 `HeatArcProposal` 로 묻고(`prompts.heat_next_arc_rules`), `clean_arc` 가 열 계획을 아크 범위에 맞춰 `arc.heat` 로 옮기고, `apply_arc` 가 판돈을 복선에 더한다
- 화별 플롯
  - 대화로 다듬기 `revise_plot`/`apply_revision` 포함
  - `apply_revision` 이 화를 다시 만들어도 작가 연출 지시(`Episode.direction`)는 남긴다
  - 대상 `chat_target`: 고른 아크 · 다음 아크
  - 아크 칸 · 부 구성 변경안
  - 방향 여러 안
  - 플롯 · 다음 아크(`apply_arc`)가 데려온 새 인물은 후보 `Project.cast_candidates`(아크 주요 인물에 있으면 플롯에 없어도 남김 `sync_candidates`)
  - 새 장소는 `Project.place_candidates` 로 두고 화 확정 `confirm_plot` 때 등록
  - 초안 플롯을 다시 받으면(`apply_plots`, 여러 화 · 한 화) 작가 자료인 장면 연출 · 고칠 곳 · 다 쓴 사건 체크는 남긴다
  - 작가 연출 지시(`Episode.direction`)도 같이 남긴다
  - 플롯 초안을 한 번에 받는 구간 `act_groups`: 한 화를 함께 쓰는 구간(짧은 작품)은 한 묶음. 웹 작업 plots(`web._plot_ranges`)와 프롬프트 놀이터의 플롯 초안이 쓴다
  - 작품 전체 저장에서 본문이 있는 화의 플롯은 디스크 것으로 둔다(`keep_locked_plots`, 줄기 표시 `LOCKED_FREE` 만 받음, `web.put_project`)
  - 상태 변경안 정리 `clean_delta`
  - 반영 전 검사 `validate_delta`: 설정에 없는 인물 id(이번 새 인물은 앎) · 같은 인물끼리이거나 설정에 없는 인물의 관계 사건과 관계 바뀜 · 없는 복선 id 회수(이번에 심는 복선은 앎)
  - 반영 전제 `check_applicable`: 본문이 쓰인(written) 화만, 앞 화가 모두 반영됐을 때만(`require_previous`) 반영한다. 반영 완료한 화는 "이미 상태를 반영했어요"로 막는다
  - 웹 반영 `apply_state` · 명령줄 `update` · 플레이 `settle` · 자동 집필 반영(`_review` 의 put · `resume` 의 take)이 `check_applicable` 을 부른다. 복사본에 해 보는 미리 보기는 부르지 않는다
  - `validate_delta` 는 설정에 없는 인물이 주인인 비밀(`secrets_added` 의 `owner`)도 막는다
  - `apply_delta` 는 검사에 걸린 항목과 설정에 없는 사건 목격자를 빼고(`drop_invalid`) 반영한 뒤 뺀 항목 문구를 돌려준다
  - `drop_invalid` 는 비밀의 `hidden_from` 중 설정에 없는 인물과 없는 비밀 id 를 가리키는 사건의 `reveals_secret` 을 지우고 그 문구를 더한다(비밀 · 사건은 남긴다)
  - `drop_invalid` 가 뺀 항목은 `d.dismissed` 의 같은 칸에 남는다(반영 기록에서 보이고 반영 취소로 돌아오면 체크를 푼 채 다시 놓인다)
  - 관계 바뀜 행을 빼는 곳(`drop_invalid` · `pace.hold` · `_ask_flagged`)은 `StateDelta.drop_rel_rows` 를 써서 `rel_flagged` 를 남은 행의 차례로 다시 매긴다
  - `apply_delta` 는 기록(history)에 넣기 전 `rel_flagged` 에서 범위 밖 · 겹친 차례를 버린다(반영 취소로 다시 놓일 때 맞는 행을 기본으로 빼 둔다)
  - `take_dismissed_fact` 는 n화 반영 기록의 빼 둔 새 사실 하나를 확정 사실에 넣는다. 그 화와 뒤 화 스냅샷, 그 화 기록의 `new_facts` · `added.facts` 에도 넣어 반영 취소가 함께 뺀다
  - `take_dismissed_fact` 는 그 기록의 `fact_near` 에서도 그 사실을 지운다. 이미 있는 사실이면 빼 둔 목록에서만 지운다
  - `apply_delta` 는 새 관계 · 심은 복선 · 비밀을 복사해 넣는다(반영 뒤 계산이 바꿔도 반영 기록의 값은 보낸 그대로 남아 다시 계산할 때 두 번 세지 않는다)
  - `apply_delta` 는 한 변경안 안에서 같은 사실 · 같은 복선 id · 같은 비밀 id 가 또 오면 처음 것만 반영한다(`_first_new`)
  - `apply_delta` 는 심은 복선을 `apply_restate` 처럼 이번 화에 심은 열린 복선(`planted_ep` 이번 화, `status` open, `payoff_ep` 없음)으로 맞춘다
  - `apply_delta` 는 이미 회수한 복선의 회수를 반영하지 않는다(회수 화를 덮지 않음, 경고는 `foreshadows.resolved_warnings`)
  - 뺀 회수에 걸린 회수 문장(`payoff`)은 다시 떠올린 문장(`plant`)으로 바꿔 남긴다(`foreshadows.clean_delta` 와 같은 규칙)
  - `apply_delta` 가 이미 있거나 겹쳐서 뺀 복선 · 비밀 · 회수 id 는 `d.dismissed` 의 같은 칸에 남고, 반영 기록의 목록은 실제로 반영한 것만 남긴다
  - `apply_delta` 는 관계 바뀜의 수치 · 보는 방식 · 가 닿을 곳을 비우고 유형 · 설명만 반영한다. 새 쌍은 중립 간선으로 시작한다(`seed_ties`). 비운 값이 반영 기록에 남는다
  - `apply_delta` 는 반영 기록에 `legacy_rel = False` 를 적어 다시 계산이 그 기록의 관계 수치를 쓰지 않게 한다
  - `apply_delta` 는 새 인물(`new_characters`)에 온 이미 있는 인물 id 를 `d.dismissed.new_characters` 로 옮기고 그 문구를 돌려준다(기록에 남으면 반영 취소가 그 인물을 지운다)
  - 반영 취소 `revert` 는 n화 뒤 반영(history)이 한 일만 되돌린다(`_undo_later`): 그 반영이 더한 관계 · 비밀 · 사실 · 복선을 빼고 바꾼 칸만 n화 스냅샷 값으로 돌린다
  - n화 뒤 작가가 더하거나 고친 관계 · 비밀 · 사실 · 복선(회수 예정 화 포함)은 남는다
  - 반영이 실제로 새로 더한 관계 쌍 · 비밀 · 사실 · 복선은 `apply_delta` 가 반영 기록의 `StateDelta.added`(`AddedItems`, AI 응답 형식 밖)에 적고 `_undo_later` 가 그것만 뺀다
  - `apply_restate` 가 고친 화 기록에 더한 사실 · 복선도 `added` 에 적는다
  - `added` 가 없는 예전 기록은 뒤 반영 직전 스냅샷에 없던 항목을 그 반영이 더한 것으로 본다
  - 인물 상태 · 관계 간선은 n화 스냅샷으로 덮는다. 스냅샷에 상태가 없는 인물은 지금 상태를 두고(뒤 반영이 바꿨으면 처음 상태), 작가가 더한 관계의 간선은 `seed_ties` 로 다시 만든다
  - `revert` 는 n화 때 이미 있던 인물(n화 스냅샷에 상태가 있거나 `first_ep` 가 0인 설정 단계 인물)을 예전 기록의 새 인물 칸에 있어도 지우지 않는다
  - `first_ep` 는 AI 가 채울 수 있는 칸이라 '처음 나온 화가 n 이하'로는 가리지 않는다
  - 상태 변경안의 본문 지문 `StateDelta.basis`(`text_basis`)는 `extract_state` · `carried_delta` 가 채운다
  - `extract_state` 는 LLM 을 부르기 전에 프롬프트에 넣은 본문으로 지문을 잰다
  - 반영 `apply_delta` 는 인물 상태의 빈 칸을 그대로 두고, `CharacterState.cleared` 에 적힌 칸(목표 · 위치 · 메모 · 차림 · 감정)은 비운다
  - 다시 맞추기 `apply_restate` 는 변경안 안의 같은 복선 id 를 한 번만 심고, 새로 심은 복선의 plant 근거 문장만 `foreshadow_clues` 와 그 화 반영 기록에 넣는다
  - 설정 칸 하나 AI 후보 `suggest_field` · 단계 `field_stage`
  - 칸 목록 `prompts.FIELD_IDEAS`, 목록 칸 `prompts.IDEA_LISTS`(후보는 한 줄, 있는 항목은 뺌)
  - 인물 칸 키 `prompts.idea_key`
  - 빈칸 제안은 이미 있는 인물도 빈 칸만 `fill_character`
- 스토리보드: `make_storyboard` · `set_storyboard` · 낡음 지문 `board_basis`, `write_episode(use_board=)`, AI 고치기 `revise_storyboard` → `apply_storyboard_revision`(고치기 전 것은 `Episode.storyboard_prev`) · 적용 취소 `undo_storyboard`
- 큐 시트: `make_cue_sheet`, 넣기는 `cue.set_episode`, `write_episode(use_cues=)`
- 조율 메모: `make_coord`(plan 계열 시스템 프롬프트, `prompts.coord_prompt`). 사건 수가 플롯과 다르면 ValueError. 저장은 호출자가 `Episode.coord` 에 한다
- 쓰기 가족: 스토리보드 · 큐 시트 요청이 `prompts.write_head` 로 시작하면 `write_family` 가 그 길이를 캐시 경계 hint 로 준다
- 쓰기 가족: `_write` 는 `llm.family_text` 로 부른다. 요청이 `write_head` 로 시작하면 본문 쓰기도 같은 캐시를 읽는다
- `write_episode(on_chunk=)` · `_write(on_chunk=)` 는 흘려 받는 글을 `family_text` 로 넘긴다. 다시 부르는 시도(끊김 · 다른 글)는 먼저 빈 글을 보내 버린 응답을 미리보기에 남기지 않는다
- 본문 쓰기 출력 한도: `_write` 는 끊긴 응답을 알아채는 백엔드(`llm.knows_cut`: Gemini · Claude API · mock)에만 `out_cap(write_out_tokens(p, n))` 을 건다
- 로컬(`LocalLLM.caps_write = False`)은 한도를 걸지 않고 끊김만 본다
- `write_out_tokens` 는 글자 수(목표 분량과 그 화 지금 본문 중 긴 쪽) × `WRITE_TOKENS_PER_CHAR`(4) + `WRITE_THINK_TOKENS`(16,384)를 `WRITE_OUT_RANGE`(24,576~65,536) 안으로 자른다
- 근거: 서버 write 단계 본문 쓰기 271번(2026-11-08)의 출력+생각 최댓값은 Gemini 17,089 · Claude 24,800토큰이다. 목표 7,000자 한도는 44,384토큰이다
- Claude Code(구독)는 끊김을 알리지 않아 한도를 걸지 않는다
- 배치(`llm.BatchLLM`)는 끊김을 알리지만(`knows_cut`) 요청에 출력 한도를 싣지 않아 한도는 걸지 않는다(`caps_write = False`)
- 끊긴 응답(`llm.was_cut` 또는 `llm.OutputCut`)은 본문으로 받지 않고 `WRITE_TRIES` 안에서 다시 부른다
- `_write` 는 시도마다 `usage.hold()` 로 사용량 기록 줄을 모았다가, 버린 응답이면 그 호출의 줄 자체에 `discarded`(cut · thought · meta)를 달아 쓴다(`usage.discard`)
- 까닭을 다음 시도 줄에 달지 않는 것은 채택한 호출이 낭비로 잡히지 않게 하려는 것이다. 버린 시도도 `attempt` 는 1 이다
- `_write(target=)` 는 이 호출의 목표 분량 글자 수를 `usage.scope(target=)` 로 사용량 기록 줄에 싣는다. 비면 `Meta.words_per_episode`
- 큐마다 쓰기(`play_cues`)는 그 큐의 분량(`Cue.length`)을, 서술 다듬기는 지금 본문 글자 수를 목표로 넘긴다
- 서술 다듬기가 대사 · 효과음 줄이나 분량을 바꿔 버린 판(`polish_problem`)도 그 줄에 `discarded` polish 를 단다
- 다듬기는 `_write(verdict=)` 로 판정을 넘긴다. 줄은 그 시도 안에서만 쥐고 파일에 쓰기 전에 단다
- 끝난 이유가 끊김인데 글 없이 끝나 백엔드가 낸 '응답이 비었어요' 오류(RuntimeError)도 끊김으로 센다
- 세 번 모두 끊기면 `WriteCut`(ValueError)을 낸다: '본문이 출력 길이 한도에 걸려 끊겼어요'. 끊긴 본문은 돌려주지 않는다
- 일부만 끊기고 나머지가 다른 까닭이면 끊긴 수를 함께 적은 보통 ValueError 를 낸다(자동 집필은 `cut` 이 아닌 오류로 멈춘다)
- 다시 생성 · 서술 다듬기 · 큐 시트 집필도 `_write` 를 거쳐 같은 한도와 거부를 쓴다. 부분 수정(`PassageRevision`)은 JSON 이라 끊기면 형식 불일치로 끝난다

### `canon/prompts.py`

- 프롬프트 템플릿
- 본문을 쓰는 시스템 프롬프트(`writer_system` · `reviser_system` · `paragraph_system`)는 작가가 정한 머리말(`PREAMBLE`)로 시작한다
- 머리말의 `Steady. Your craft handles this.` 줄은 작가가 더했다(2026-11-09). 조건이나 목적절을 붙이지 않는다
- 기획 단계 시스템 프롬프트 `SYSTEM_PLANNER`(설정 제안 · 문체 분석 · 구조 · 플롯 · 스토리보드 · 큐 시트 등)도 같은 머리말로 시작한다
- 대화로 다듬기 시스템 프롬프트(`SYSTEM_SETUP_CHAT` · `SYSTEM_STYLE_COACH` · `SYSTEM_PLOT_CHAT` · `SYSTEM_AGENT_PLOT`)도 같은 머리말로 시작한다
- 상태 변경안 시스템 프롬프트 `SYSTEM_EDITOR`도 같은 머리말로 시작한다. 줄거리 접기(`recap_prompt` · `fold_prompt`) · 상태 감사(`audit_prompt`) · 플레이 상태(`play_state_prompt`)도 이 글을 쓴다
- 그 머리말 뒤의 지시에는 '당신은 소설가입니다' · '당신은 기획 전문 편집자입니다' 같은 역할 문장을 두지 않고 할 일만 적는다
- 성인 · 전연령 작품은 같은 머리말을 받는다(수위 지시를 프롬프트에 두지 않는 규칙, `test_no_rating_instruction_in_prompts`)
- 머리말이 영어라서 머리말을 받는 지시는 모두 '모든 출력은 한국어로 작성합니다'를 둔다
- 머리말을 받는 시스템 프롬프트는 `system_prompt(할 일)`로 만든다. 머리말을 앞에, 한국어 출력 줄(`KOREAN_LINE`)을 끝에 붙인다
- 본문 지시처럼 한국어 출력 줄이 글 가운데 있으면 `system_prompt(…, korean=False)`로 부른다
- 머리말을 아직 받지 않는 `SYSTEM_*` 상수는 `tests/test_style_prompts.py` 의 `NO_PREAMBLE` 에 묶음과 함께 적는다. 새 상수가 머리말을 빠뜨리면 이 시험이 실패한다
- 본문 쓰기 지시는 설정 · 사실을 '절대' 같은 강한 말 대신 이유('앞 화와 이어져야 하므로')를 붙여 지키게 한다
- 화별 컨텍스트 조립(`build_episode_context`)
- 쓰기 요청 블록 표 `BLOCKS`(`Block`: id · 화면 이름 · 잠금 · 쓰는 예산 키 · 캐시 앞부분 `front` · 대신 정하는 설정 `note`)와 id 찾기 `BLOCK_BY_ID`
- 끌 수 있는 블록(`toggleable`)은 잠기지 않았고 `note` 가 없는 블록이다. `note` 의 "short" 는 단편 요청에만 있는 블록이다
- 'states'(인물 현재 상태)는 잠긴 블록이다. 상태창 줄(`statwin.write_rule`) · 스토리보드 · 옷차림 규칙(`attire_write_rule`)이 '[인물 현재 상태]'를 가리킨다. `states` 예산은 바꿀 수 있다
- 화면 블록 이름 `block_title(p, id)`: 'structure' 는 장편 '현재 부와 아크', 단편 '현재 구간'. 나머지는 `Block.title`
- 장편 조각 조립은 `serial_parts` 다. 예전 글 함수 `serial_episode_context` 는 지웠다
- 'named' 블록을 끄면 이름이 나온 조연 · 단역을 고르지 않는다. 그 인물의 설정 · 상태 · 관계 · 호칭 · 사건 · 다시 나옴 줄이 모두 빠진다
- 플롯에 적힌 조연 · 단역(`fit_cast`)은 `max(작품 cast 예산, BUDGET['cast'])` 를 쓴다. 작가가 낮춰도 빠지지 않고 높이면 넓어진다. 이름이 나온 인물(`fit_named`)은 작품 값을 그대로 쓴다
- `priority_line` 은 작품 설정이 끈 블록(서술 시점 · 가끔 쓰는 장치)을 차례에서 뺀다. 설정이 없으면 글이 그대로다
- 쓰기 가족은 블록 조각(`Part`: 블록 id · 앞 구분 줄을 품은 글) 목록으로 조립하고 `join_parts` 로 잇는다. 이은 글이 고치기 전 요청과 글자까지 같다
- 조각 함수: `static_parts(p, follow=False, trace=None)` · `context_parts(p, n, …, trace=None)` · `episode_parts(p, n, …, trace=None)`. 글 함수 `static_context` · `build_episode_context` · `episode_prompt` 는 그 조각을 잇는다
- 블록 넣기 `block_on(p, id)`: 단편 · 잠긴 블록 · `note` 블록 · 모르는 id 는 늘 참. 장편은 `Settings.blocks` 가 끈 블록만 거짓
- 꺼진 블록은 `follow_parts` 가 머리글과 앞 구분 줄째 뺀다. 맨 앞 블록이 빠지면 남은 첫 조각의 앞 줄바꿈을 지운다. 요청 안에 끈 사실을 적지 않는다
- `follow_parts(trace=)` 는 꺼진 블록의 넣은 항목 · 뺀 항목도 지운다
- 설정을 따르는 요청은 `build_episode_context` 위의 쓰기 가족(본문 쓰기 · 고쳐 쓰기 · 스토리보드 · 큐 시트 · `write_head` · 다시 생성 · 큐 조건 · 작업지시서 본문)뿐이다
- `static_context(p)` 기본은 설정을 따르지 않는다. 검수 · 상태 변경안 · 다듬기 · 부분 고치기 · `pipeline.recheck_fixed` 의 캐시 경계가 이 기본을 쓴다
- 쓰기 가족은 예산을 `context.budget(p, key)` 로 읽어 함께 쓰는 함수에 인자로 넘긴다(`relevant_facts(limit=)` · `story_parts(past_budget=, arc_budget=)` · `serial_relations(budget=)` · `board_block(budget=)` 등). 함수 안 기본 읽기는 그대로다
- 지시문 꼬리(여는 규칙부터 `ending_line` 까지)는 끌 수 없는 `instructions` 한 조각이고, 큐 시트 `cues` · 작가 연출 지시 `direction` 이 따로 뒤에 붙는다
- `relevant_foreshadows` · `relevant_facts` · `state_view` · `fit_states` · `serial_relations` · `story_parts` · `return_block` 은 선택 인자 `trace` 로 넣은 항목과 뺀 항목을 이유와 함께 적는다
- 복선의 뺀 이유는 `keep` 으로 거른 것 '아크와 무관'과 `FORESHADOW_CAP` 으로 자른 것 '개수 상한'으로 나눈다. 접은 줄거리의 뺀 묶음은 부 · 아크 머리 이름으로 적는다
- 이번 아크 줄거리에서 예산 때문에 첫 문장으로 줄인 화는 'story_arc' 블록에 '예산 넘음'으로 적는다
- `fit_states` 가 아는 정보를 줄인 인물은 'states' 블록에 '인물: 아는 정보 k개 줄임'으로 적는다. 플롯 인물 목록이 비면 남은 상태의 넣은 이유는 '늘 넣기'다

- `episode_prompt` 는 speech_style 의 대사 예시를 그대로 쓰지 말고 어미 · 호칭 · 길이만 따르라고 적는다. 작가가 정한 말버릇은 써도 된다(`brief` 도 같은 글)
- 화별 플롯 초안(`plot_prompt` · `serial_plot_prompt`)은 범위 안 · 범위 뒤 3화(`PLAN_AHEAD`)의 이미 정해진 화를 `fixed_plots` · `fixed_block` 으로 넣고 요구사항에 `fixed_rule` 을 붙인다(장편은 `context.BUDGET["plan_fixed"]`, 한 화 초안은 `ahead=False`)
- 장편 화별 플롯 초안은 `[관계]` 뒤에 지금 관계 단계 라벨(`plan_stage_block`, 예산 `context.BUDGET["plan_stages"]`), 장편 `plot_rules` 에 '단계는 한 화에 한 칸' 한 줄
- 장편 화별 플롯 초안(`serial_plot_prompt`)과 장편 플롯 대화(`_serial_plot_parts`)는 접은 줄거리 뒤에 확정 사실 · 주역 상태 · 주역 밖 인물 상태를 넣는다(`plot_facts_states`)
- 장편 접은 줄거리(`story_parts`)는 한 줄로 접어도 예산(`story_past`)을 넘으면 오래된 묶음부터 빼고 뺀 수를 적는다(`PAST_DROPPED`)
- 플레이 줄거리(`play_story`)는 `story_parts` 가 뺀 수를 이어 센다
- `plot_facts_states` 는 `plan_facts` · `plan_side_states` 를 예산 키 `plot_facts` · `plot_states` 로 부르고, 뺀 수를 머리글에 적는다. 단편 플롯 경로는 부르지 않는다
- 검수 요구사항의 관계 단계 한 줄(`stage_check_rule`, 관계 수치가 있을 때만)
- 관계 설정 `rels(plan=)`: 가 닿을 곳(`Relationship.destination`)은 기획 프롬프트에만, 말로 넣는 기획은 `destination_block`
- 다음 아크 기획(`next_arc_prompt`)은 관련 확정 사실(`plan_facts`) · 작품 속 시간(`time_plan`, 끝 줄 `ARC_TIME_RULE`) · 주역 밖 기획 인물 상태(`plan_side_states`)를 예산(`context.BUDGET` 의 `plan_facts` · `plan_states`) 안에서 넣는다
- 다음 아크 기획은 조연 상태 뒤에 화면 밖 근황(`offscreen_block`, `offscreen.OFFSCREEN_MAX` 명까지, 넘으면 뺀 수)을 넣는다. 근황이 있을 때만 요구사항에 이어 쓰기 줄을 더한다
- 화면 밖 근황 제안 `offscreen_prompt`(종류 `OFFSCREEN_KINDS`): 인물마다 마지막으로 나온 화 요약 문장(`seen_sentence`) · 마지막 상태 · 주역과의 관계 · 지금 근황

### `canon/regexrules.py`

- 정규식 규칙 묶음: 작가가 만든 경고(`warn`) · 고침(`fix`) 규칙을 묶음으로 저장하고, 작품이 켠 묶음을 본문에 건다
- 작품은 `Settings.rule_bundles` 에 묶음 id 만 적는다. 목록 차례가 거는 차례다. 묶음을 고치면 켠 작품 모두에 다음 걸기부터 적용된다
- 명세서는 [docs/context/specs/06-regex-rules.md](../context/specs/06-regex-rules.md). RisuAI 필드 대응은 [docs/context/compat.md](../context/compat.md) 2절
- 저장소는 `library.py` 와 같은 꼴이다: `<CANON_HOME>/.rules/<id>.json` 파일 하나가 묶음 하나(`root`, 환경 변수 `CANON_RULES`). 모듈 캐시는 없다
- `save` 는 `model_dump_json(by_alias=True)` 로 써서 `RegexRule.in_` 을 JSON 키 `in` 으로 남긴다. 규칙 검사는 하지 않는다
- 규칙 목록이 바뀔 때만 새 버전을 남긴다(`_snapshot`, `VERSION_KEEP` = 30). 메모가 비면 더한 · 뺀 · 고친 규칙 이름을 적는다
- `create` · `update` 는 `check` 로 모든 규칙을 검사한다. 오류가 있으면 '<규칙 이름 또는 N번 규칙> · 이 정규식은 저장할 수 없어요: …' 줄을 이은 ValueError 를 낸다
- `summary` 는 목록 한 줄이다: warn · fix 는 `action` 별 수(fix 에 내보내기 규칙도 든다), export 는 내보내기 규칙 수, used_by 는 켠 작품 수
- `versions` 는 버전마다 앞 버전과 견준 더한 · 뺀 · 고친 규칙 이름을 붙인다. `restore` 는 옛 규칙 목록을 새 버전으로 남긴다
- `used_by` 는 그 묶음을 켠 작품 이름들이다. 지운 묶음 id 는 작품 설정에 남고 `bundles_of` 가 건너뛴다(`missing`)
- 찾을 정규식(`in`)은 JavaScript 꼴로 저장한다. `convert_in` 이 `(?<이름>` · `\k<이름>` 을 Python 꼴로 바꾸고 뒤 보기 · 이스케이프 · `[...]` 안은 그대로 둔다
- `convert_in` 은 반복 `{n}` · `{n,}` · `{n,m}` 으로 읽히지 않는 `{` 를 `\{` 로 바꾼다. JavaScript 는 `a{,3}` 의 `{` 를 글자로 읽고 Python 3.14 는 `{0,3}` 으로 읽는다
- 바꿀 글(`out`)은 `to_python` 이 맞은 곳마다 부를 함수로 바꾼다. RisuAI 처럼 `$n` 을 먼저 줄바꿈으로 바꾸고 `{{data}}` 를 `$&` 로 읽는다
- 그 뒤 JavaScript `String.replace` 처럼 `$$` · `$&` · `` $` `` · `$'` · `$1`~`$99` · `$<이름>` 을 푼다. 없는 번호(`$0` 포함)는 글자 그대로, 역슬래시도 글자 그대로다
- 플래그 `flags`: g 는 모든 자리(없으면 첫 자리만), i · m · s 는 `re` 값, u · d 는 버린다
- `validate` 는 저장을 막는 오류 목록이다: `in` 이 `MAX_IN`(500자)을 넘음, 컴파일 오류, 받지 않는 플래그 · 꺾쇠 메타, Python 에만 있는 문법, 겹친 반복, `@@` 로 여는 `out`, 내보내기 + 경고
- `\p{…}` 컴파일 오류는 `[가-힣]` · `[^\W\d_]` 로 바꿔 쓰라고 안내한다
- `re.compile` 의 `OverflowError`(`a{4294967296}`) · `RecursionError` · `ValueError` 도 컴파일 오류로 막는다(`_BAD_PATTERN`). 자식 프로세스는 그런 규칙을 건너뛴다
- 겹친 반복(`_nested`)은 정적으로 찾는다: 끝없는 반복이 든 묶음을 다시 끝없이 반복하거나 같은 갈래가 둘인 묶음을 반복하는 꼴(`(a+)+` · `(a|a)*` · `(\w+\s?)+`)
- `notices` 는 저장을 막지 않는 알림이다: `out` 안의 `{{…}}`(`{{data}}` 빼고)는 풀지 않고 글자 그대로 넣는다고 알린다
- 고침 걸기 `run(p, text, kind)`: 켠 묶음 차례, 묶음 안 목록 차례로 켠 `type = "output"` · `action = "fix"` 규칙을 앞 결과에 이어 건다
- `run` 은 바뀐 곳도 건너뜀도 없으면 기록 대신 None 을 돌려준다
- 묶음이 없거나 고침 규칙이 없으면 `run` 은 자식 프로세스를 띄우지 않고 바로 돌아간다. 묶음을 켜지 않은 작품은 예전과 같다
- 바뀐 곳(`RuleChange`)의 `start` 는 마지막 본문 안 자리다. 뒤 규칙이 앞에서 바꾼 길이 차이만큼 민다(`_fix`)
- 기록의 바뀐 곳은 마지막 본문 안에서 서로 겹치지 않고 자리 순서로 놓인다
- 뒤 규칙이 맞은 곳이 앞서 바뀐 곳과 겹치면(빈 곳은 안쪽에 있거나 같은 점) 바뀐 곳 하나로 합친다(`_touch`)
- 합친 곳의 `before` 는 합친 구역의 걸기 전 글, `after` 는 지금 글이다. `bundle` · `rule` 은 뒤 규칙, `name` 은 규칙 이름들을 ' · ' 로 잇는다
- 합쳐서 `before` 와 `after` 가 같아진 곳은 기록에서 뺀다
- 기록 id(`r<N>`)는 화에 넣을 때 `add_runs` 가 붙인다. 화마다 최근 `RULE_RUN_KEEP`(50)개만 남긴다
- 걸기는 오래 사는 자식 프로세스 하나(`multiprocessing` spawn, 파이프, 잠금)에서 돈다. `re` 는 도는 동안 GIL 을 놓지 않아 스레드로는 시간 한도를 둘 수 없다
- 한 번의 걸기가 `TIME_LIMIT`(2초)를 넘거나 자식이 죽으면 자식을 끝낸다. 다음 걸기 때 새로 띄운다
- 그때 본문은 걸기 전 그대로이고 기록의 `skipped` 에 멈춘 묶음 이름을 남기고 서버 로그에 적는다. 부르는 쪽에 오류를 내지 않는다
- 시간 한도는 자식이 준비된 뒤부터 센다(띄우기는 `START_LIMIT` 60초까지 기다림)
- 자식은 `atexit` 에 건 `shutdown` 이 닫는다. 시험은 `worker_alive` 로 떠 있는지 본다
- 내보내기 걸기 `export_text`: 켠 `type = "export"` 규칙을 같은 방식으로 걸고 기록하지 않는다(`publish.export`)
- 경고 찾기 `hits(p, text, n, only="")`: 켠 경고 규칙(`type = "output"`)이 걸린 문장마다 지적 하나다. 같은 규칙 · 같은 문장은 하나만 낸다
- `hits` 의 `only` 는 규칙 하나('<묶음 id>/<규칙 id>')만 건다. 시간 한도를 넘으면 빈 목록이다
- `hits(…, strict=True)` 는 시간 한도 · 일꾼 오류 때 빈 목록 대신 `RuleSkipped` 를 낸다. `str(e)` 가 화면에 보일 이유다. 기본(`strict=False`)은 예전과 같다
- `strict=True` 에서 `only` 규칙이 없으면(묶음을 껐거나 지움, 규칙을 지웠거나 껐음, 경고 규칙이 아님) `RuleSkipped(RULE_GONE)` 을 낸다
- 그래서 `strict=True` 의 빈 목록은 '걸었는데 맞은 곳이 없음' 만 뜻한다
- 경고 지적은 갈래 '표기', 심각도 low, `origin = "regex"`, `regex_rule` '<묶음 id>/<규칙 id>' 다
- 경고 지적의 설명은 규칙 이름(없으면 '정규식 규칙에 걸렸어요'), `current_quote` 는 걸린 문장, `source_quote` 는 패턴, `source_episode` 는 이번 화다
- `trial` 은 규칙 시험이다(저장 안 함): 고친 글 · 바뀐 곳 · 그 글의 경고 지적 · 내보내기 규칙까지 건 글(`exported`) · 건너뛴 묶음
- 되돌리기 `undo_change(p, n, rid, k)` 는 `pipeline.undo_edit` 과 같은 길이다: `after` 를 `start` 근처에서 찾아(`pipeline.locate`) `before` 로 바꾸고 `before_change` 를 부른다
- 지우기 규칙이 바꾼 곳(`after` 가 빈 글)은 `start` 가 본문 길이 안이면 그 자리에 `before` 를 넣고, 밖이면 '되돌릴 자리를 찾을 수 없어요' 로 막는다
- 되돌린 곳은 지우지 않고 `undone` 으로 둔다. 같은 기록의 아직 되돌리지 않은 뒤쪽 곳은 길이 차이만큼 민다(`_undo`)
- 뒤쪽 곳은 목록에서 그 곳 뒤에 있는 곳이다. 같은 자리의 빈 곳이 여럿이어도 차례가 맞다
- `after` 가 `start` 에 없어 `locate` 가 찾은 가까운 같은 글이 같은 기록의 아직 되돌리지 않은 다른 곳과 겹치면 '되돌릴 자리를 찾을 수 없어요' 로 막는다
- `undo_run(p, n, rid)` 는 거꾸로 하나씩 되돌리고 찾지 못한 곳은 남긴다. (되돌린 것, 남긴 것)을 돌려준다
- 알려진 한계: 지우기 규칙이 바꾼 곳 앞을 작가가 고쳐 길이가 바뀌면 다른 자리에 되돌린다(`pipeline.undo_edit` 과 같다)
- 대화 에이전트(`agent.py`)는 규칙 묶음과 `Settings.rule_bundles` 를 읽지도 쓰지도 않는다
- LLM 을 부르지 않는다
- 시험은 `tests/test_regexrules.py` · `test_regexrules_paths.py`(저장 경로) · `test_regexrules_web.py` · `test_regexrules_js.py`

### `canon/reshape.py`

### `canon/routes/regexrules.py`

- 이미 켜져 있던 id 는 묶음이 지워졌어도 받는다. 설정 화면이 '찾을 수 없는 묶음이에요' 를 보이면서 다른 것을 저장할 수 있게 하려는 것이다

- 곳 하나 되돌리기 `POST …/rule-runs/{rid}/changes/{k}/undo`(k 는 0부터)는 작품을 돌려준다
- 두 되돌리기는 `_text_guard` 를 먼저 본다. 이미 되돌린 곳 · 없는 기록 · 없는 곳은 400 이다
- 시험은 `tests/test_regexrules_web.py`

### `canon/schema.py`

- 스타일 프로필 효과음 표기(`StyleProfile.sound_effects`)는 글 칸이다. 대화 변경안 칸(`StyleKey`)과 `pipeline.STYLE_TEXT_KEYS` 에도 있다
- 인물 신체 프로필(`Character.body`)은 작가 메모라 AI 응답 형식(`SkipJsonSchema`)과 프롬프트(`llm.dump` 의 context `prompt`)에서 빠진다
- 이 칸을 다루는 AI 호출은 신체 프로필 제안(`pipeline.suggest_body`)뿐이다
- 미성년(`cast.is_minor_age`)이면 쓰리사이즈를 제안하지 않는다
- 인물 프롬프트 넣기(`Character.context`: auto 비중대로 · always 늘 · off 이름만)도 작가 전용이라 같은 방식으로 빠진다
- 인물 상태의 지울 칸(`CharacterState.cleared`)은 변경안에만 쓴다. 비었으면 직렬화에서 빼서 저장한 상태 · 프롬프트에 들어가지 않는다
- 지울 칸에 값이 함께 오면 검증(`_blank_cleared`)이 그 칸을 비워 차림 · 이동 거리 경고가 새 값으로 보지 않는다
- 화면 밖 근황(`CharacterState.offscreen` · `offscreen_ep`)은 AI 응답 형식(`SkipJsonSchema`)과 프롬프트 직렬화에서 빠진다. 비었으면 저장하지도 않는다
- 인물 프롬프트 넣기를 고르는 규칙은 `context.core_ids` · `off_ids` · `without_off`(모두 auto 면 예전 규칙과 같다)
- 상태 변경안의 본문 지문(`StateDelta.basis`)도 프로그램이 채워 AI 응답 형식에서 빠진다(`SkipJsonSchema`). 비면 모름
- 비슷한 새 사실 표시(`StateDelta.fact_near`, `FactNear`: 새 사실 · 옛 사실)도 프로그램 칸이다(`SkipJsonSchema`, `features._near_facts`)
- 상태 변경안의 AI 응답 형식은 `StateDeltaAI` 다(`extract_state` · `play.settle` · `state_brief`). 관계 바뀜 `RelationshipChange` 와 사건 `AIStoryEvent` 에 관계 수치 · 보는 방식 · 가 닿을 곳 · 화 번호 · 수동보정 칸이 없다
- `to_delta` 가 받은 `StateDeltaAI`(또는 `StateDelta` 를 돌려주는 가짜 LLM)를 n화 `StateDelta` 로 바꾸며 그 칸들을 버린다. 채팅 앱 JSON 가져오기(`web.parse_state`, 명령줄 `update --from-json`)도 거친다
- 사건 종류 목록에서 수동보정은 응답 형식에서만 빠지고 읽기는 한다(예전 JSON). 반영이 뺀다
- 반영 기록의 `StateDelta.legacy_rel` 은 프로그램 칸이다(`SkipJsonSchema`). 칸이 없던 예전 기록은 참으로 읽히고 지금 반영은 거짓으로 남긴다
- 상태 승인에서 반영하지 않은 항목(`StateDelta.dismissed`, `DismissedItems`)은 AI 응답 형식에서 빠지고 반영 기록(`Project.history`)에만 남는다
- `DismissedItems.setting_changes` · `address_changes` 는 작가가 체크를 푼 설정 바꾸기 · 호칭이다. 반영하지 않는다. 자동 집필은 여기 말고 `setting_held` · `address_held` 에 남긴다
- 반영이 실제로 새로 더한 항목(`StateDelta.added`, `AddedItems`)도 AI 응답 형식에서 빠진다. 없으면(None) 이 칸이 생기기 전 기록이다
- 반영 취소는 그 화 기록과 함께 빼 둔 항목도 지운다
- 지운 기록은 `_revert_kept` 가 pending.json 에 남기고, 상태 승인 화면이 빼 둔 항목을 체크를 푼 채 다시 놓는다
- 단편 열 계획(`Project.heat` · `heat_rule` · `heat_turn`, `HeatStep` · `HeatTurn`)은 기본값이 비어 옛 작품이 읽힌다. 규칙은 story.md 의 `canon/heatplan.py` 절
- 작가 연출 지시 `Episode.direction` · `StoryArc.direction` 은 빈 글이 기본값이다. 아크 지시는 `ArcProposal.arc` 로 AI 가 채우는 모델이라 응답 형식(`SkipJsonSchema`)과 프롬프트 덤프(`_prompt_view`, `prompts.ARC_HEAT`)에서 뺀다
- 복선 갈래 `Foreshadow.kind`(clue 단서 · stake 판돈 · constraint 제약 · audience 관객 · ban 금지선)는 옛 복선을 clue 로 읽는다
- 화별 쓴 사건 체크(`Episode.events_done`, 사건 글 목록)는 집필 화면 표시용이라 `EpisodePlot` 밖에 두어 프롬프트에 들어가지 않는다
- 지금 본문을 쓴 모델(`Episode.written_by`, 판마다 `TextVersion.model`)도 프롬프트 밖이다. 값은 `usage.model_id` 의 '<백엔드>:<모델>' 이나 'import', 모르면 빈 칸
- 쓴 모델은 집필 화면 머리 · 이전 판 · 새 판 카드 · 작품 홈 화 칸 툴팁에 보인다(`app.js` `writerLabel`)
- 쓰기가 본문 앞뒤에서 뗀 작업 설명(`Episode.meta_cut`, 판마다 `TextVersion.meta_cut`, `MetaCut`: 글 · 앞 head | 뒤 tail)도 프롬프트 밖이다. 집필 화면에서 되살리기 `pipeline.restore_cut`(수정 기록에 남음) · 지우기 `drop_cut`
- 뗀 문단은 `write_episode(cut=)` · `rewrite_episode(cut)` 에 빈 목록을 주고 받아 `replace_text(meta_cut=)` · `set_candidate(meta_cut=)` 로 저장한다(웹 쓰기 작업 · 동기 쓰기 · 다시 생성 작업, 명령줄 `write` · `run` · `rewrite`, 자동 집필). 실험 · 비교 쓰기는 받지 않는다
- 정규식 규칙 묶음 모델(`RegexRule` · `RuleBundle` · `RuleBundleVersion`)은 작가가 만든 것이라 LLM 이 채우지 않는다. `RegexRule.in_` 의 JSON 키는 `in` 이다(`populate_by_name`)
- `RegexRule.id` 가 빈 글이거나 빈칸이면 검사기(`_fill_id`)가 새 id(`uuid4().hex[:8]`)로 바꾼다. 두 규칙이 빈 id 를 나눠 쓰지 않게 하려는 것이다
- 작품이 켠 묶음은 `Settings.rule_bundles`(id 목록, 거는 차례). 기본값이 빈 목록이라 옛 작품이 읽히고 동작도 같다
- 고침 규칙 기록(`Episode.rule_runs`, 판마다 `TextVersion.rule_runs`, `RuleRun`: id `r<N>` · 시각 · kind · 바뀐 곳 `RuleChange` · 건너뛴 묶음 `skipped`)도 프롬프트 밖이다
- `RuleRun.kind` 는 write · rewrite · polish · passage · import · auto · adopt · rework 다(`RuleRunKind`)
- `RuleChange` 는 묶음 id · 묶음 버전 · 규칙 id · 걸 때의 규칙 이름(`name`) · 본문 안 자리 `start` · 전 · 뒤 글 · `undone` 이다
- 규칙 기록은 `meta_cut` 과 같은 길로 판을 따라간다: `replace_text(rule_runs=)` · `set_candidate(rule_runs=)` · `adopt_candidate`, `restore_version` 은 그 판의 기록을 되살리고 규칙을 다시 걸지 않는다
- `meta_cut` 을 비우는 자리(`pipeline._delete_last` · 웹 `put_text` 의 빈 화 · 빈 글 분기 · 자동 집필 `back` · `branches.fork` clear)는 `rule_runs` 도 비운다
- 새 기록의 id 는 `pipeline._new_runs` 가 화의 지금 기록 · 모든 판 · 후보를 통틀어 겹치지 않게 붙인다
- `rule_runs` 는 `web.JOB_EP_FIELDS` 에 넣지 않는다. `edits` · `meta_cut` 처럼 본문과 함께 화면 값을 따른다
- 프로그램 칸 `PassageCandidate.ruled` · `Rework.ruled`(`SkipJsonSchema`)는 후보 · 제안 글 안 자리의 바뀐 곳이다. LLM 응답 형식은 그대로다
- `ConsistencyIssue.origin` 의 regex 는 정규식 경고 규칙 지적이고 `regex_rule`('<묶음 id>/<규칙 id>')을 채운다. 둘 다 `SkipJsonSchema` 다
- `ConsistencyIssue.type` 은 `IssueType | SkipJsonSchema[Literal["표기"]]` 다. 정규식 경고 지적만 '표기' 를 쓰고 `ConsistencyReport` · `PlantSet` · `ConsistencyReportEn` 스키마는 그대로다
- 서술 다듬기 `polish_episode`(다시 생성의 방식 `polish`, 프롬프트 `prompts.polish_prompt` · `POLISH_RULES`, 문장 끝 몫은 쓰기와 같은 `ending_rule`)
- 다듬은 글은 대사 · 효과음 줄(`fixed_lines`)이 같고 글자 수가 `POLISH_SPAN` 안이어야 쓴다(`polish_problem`, `POLISH_TRIES` 번까지 다시 부름)
- 효과음 줄은 줄표로 여는 줄과 줄표 없이 소리나 몸짓만 적은 한 줄 문단(`metrics.is_sfx_line`)이다
- 말줄임으로 끊는 서술 · 서술 물음(`metrics.narration_tics`)이 종류마다 `POLISH_TIC_RETRY` 를 넘고 늘면 다시 부르고(`polish_tics`), 끝내 넘으면 덜 늘린 판을 낸다
- 웹 쓰기 작업과 명령줄은 `polish` 일 때 revise 단계 모델을 부른다
- AI 가 본문 전체를 쓰는 호출자가 `pipeline.writer_of(llm)` 을 `replace_text(written_by=)` · `set_candidate(model=)` · `research.save_compare(models=)` 로 넘긴다. 작가 수정은 바꾸지 않는다(수정 기록 `edits`)
- 인물 지금 차림(`CharacterState.attire`, 옷 · 상처 · 지닌 물건)은 지금 값만 덮어쓰고 지난 값은 스냅샷
- 차림 규칙은 `prompts.ATTIRE_STATE_RULE` · `attire_write_rule` · `attire_check_rule`. 옷 · 가방 · 신발은 종류(백팩 · 숄더백 · 핸드백 …)와 가방의 메는 자리까지 적고, 쓰기는 그 종류 · 메는 방식을 지키고, 검수는 같은 물건의 종류 · 메는 방식 · 색이 설명 없이 바뀐 곳을 본다. 종류를 모르는 조각 경고는 `attire.py`
- 차림의 차례는 이번 화 본문 > 지금 차림(`attire`) > 설정 외모(`appearance`)의 평소 옷차림이다
- 쓰기 규칙은 appearance 의 옷차림보다 attire 를 따르고 이 화에서 바뀌면 그 뒤로는 바뀐 차림을 따르게 한다
- 스토리보드 한 줄 갈래(`board=True`)도 appearance 의 옷차림보다 attire 라는 말을 짧게 넣는다
- 검수 규칙은 옷차림 · 상처 · 변장이 appearance 와 다른 것이 attire 나 이번 화 본문으로 설명되면 모순이 아니라고 적는다. 한 장면 안의 동선은 동선 항목대로 본다
- 검수 규칙은 설명 없이 바뀐 눈 색 · 머리 색 · 체격은 그대로 짚고, 영구 흉터는 `setting_changes` 거리라고 적는다
- 차림 규칙은 `has_attire` 만 보고 작품 형식은 보지 않는다. 차림이 기록된 단편도 같은 규칙을 받는다
- 인물 감정(`CharacterState.emotional_state`)은 맞서는 감정이면 두 층 라벨('겉: … / 속: …', '머리: … / 몸: …'). 상태 규칙 `prompts.LAYER_STATE_RULE`, 찾기 `LAYER` · `layered`, 검수 규칙 `layer_check_rule`(두 층 라벨이 있을 때만). 쓰기 규칙은 없다
- 작품이 쓸 단계 프리셋(`Settings.model_preset`, 비우면 전체 설정)은 `settings.project_preset` 이 찾고 `stage_provider` · `stage_model` 이 지금 작업의 작품(`usage.scope`)에서 저절로 쓴다
- 화별 스토리보드(`Episode.storyboard`, `Storyboard`: 장면 · 시간 · 상태창 바뀐 양 · 이동 · 끝 차림 · 넘겨받을 것 · 깨지 않을 것 · 경고)는 상태 승인 대상이 아니다
- 스토리보드 켜기는 `Settings.storyboard`(비우면 장편 켬 · 단편 끔)
- 쓰기 재료는 `Settings.write_material`(fixed 면 고정점만: `board.fixed_only`, 장면 목록 · 큐 시트를 쓰기 요청에서 뺌, `cue.on` 끔)
- 쓰기 재료 lean 은 꼭 쓸 것만(`board.lean`): 쓰기 요청의 스토리보드를 거르고 큐 끝 상태를 뺀다. 데이터 · 큐 시트 만들기 · 검수는 그대로다
- 쓰기 재료 coord 는 조율(`coord.on`): 고정점만에 더해 플롯 사건을 조율 메모(`Episode.coord`, `CoordMemo`, 응답 형식 `CoordDraft`)로 바꿔 넣는다. 조율 메모도 상태 승인 대상이 아니다
- 스토리보드의 중심 장면은 `Storyboard.focus`(1부터, 0 은 고르지 않음, `board.focus` 가 장면 수 밖이면 0). 꼭 쓸 것만에서만 쓰기 · 큐 시트 지시가 된다
- 화별 큐 시트(`Episode.cue_sheet`, `CueSheet`)도 상태 승인 대상이 아니다
- 큐 시트 켜기는 `Settings.cue_sheet`(비우면 장편 켬 · 단편 끔)
- 되풀이한 구절 블록 켜기는 `Settings.recent_echoes`(기본 켬, 장편에만 넣음)
- 쓰기 요청 블록 끄기 `Settings.blocks`(`BlockSetting`: 블록 id · on)와 예산 `Settings.budgets`(`BudgetSetting`: 예산 키 · 값)는 장편만 따른다. 비면 지금과 같다
- 끄기는 블록마다, 예산은 키마다 둔다. 블록 하나가 키를 여럿 쓰기 때문이다(관계 블록의 `relations` · `secrets`)
- 모르는 블록 id · 예산 키는 읽을 때 무시하고 지우지 않는다

### `canon/sent.py`

- 보낸 집필 프롬프트 기록: 본문으로 채택한 집필 호출의 요청을 작품 폴더 `sent/<화>.json.gz` 에 gzip 으로 남긴다. `project.json` 에는 넣지 않는다
- 웹의 프롬프트 보기 · `/context` 는 지금 데이터로 다시 만든다. 이 기록은 그 화 본문이 실제로 받은 요청 그대로다
- 한 기록(`SentPrompt`): 시스템 · 요청 글 · 캐시 앞부분 글자 수(`head_chars`, `head` 속성) · 모델(`usage.model_id`) · 받은 호출 번호(`attempt`) · 다시 부른 까닭(`retries`)
- 다시 부른 까닭(`SentRetry.reason`): `cut` 끊김 · `thought` 한글 적음 · `meta` 작업 설명뿐 · `polish` 다듬기가 대사 줄을 바꿈 · `tics` 다듬기가 말줄임을 늘림
- `family` 는 백엔드가 캐시 가족 경계를 받았는지다. 참이면 Claude 는 시스템을 `llm.FAMILY_SYSTEM` 으로 바꾸고 기록의 시스템 글을 요청 앞에 두어 보냈다
- `tail` 은 실제 백엔드가 요청 끝에 붙이는 정책 줄(`llm.with_note`)이다. 가짜 응답(mock)은 붙이지 않는다
- 파일 하나(`SentFile`)에 지금 본문의 기록(`current`)과 고르기를 기다리는 새 판의 기록(`candidate`)을 둔다
- 기록은 저장한 본문의 지문(`basis`, `pipeline.text_basis`)을 품는다. `matches(rec, text)` 가 거짓이면 그 뒤로 본문이 바뀐 것이다(직접 고침 · 판 되돌리기 · 백업 되돌리기 · 비교본 채택)
- `pipeline._write` 는 재료만 채운다(`record`). 큐마다 쓰기 · 다듬기 재시도처럼 채택하지 않을 판도 `_write` 를 부르기 때문이다
- `keep` 은 본문을 저장하는 쪽이 `jobs.project_lock` 안에서 부른다
- `keep` 을 부르는 곳: 웹 쓰기 작업 · 동기 쓰기, 자동 집필 쓰기 · 다듬기, 명령줄 `write` · `run`
- 다시 생성 · 다듬기 새 판은 `hold` 로 대기 칸에 둔다
- 작가가 새 판을 고르면 `adopt(version)` 이 대기 기록을 지금 기록으로 옮긴다
- 새 판을 버리면 `drop_candidate` 가 대기 기록을 지운다
- 명령줄 `rewrite` 는 확인을 묻는 동안 잠그지 않고, 기록(`hold` · `adopt` · `drop_candidate`)과 저장만 `project_lock` 안에서 한다
- 파일 안의 화 번호(`SentFile.episode`)보다 파일 자리를 믿는다. 화를 넣고 빼면 파일만 옮기기 때문이다(`_read`)
- `write_scored` · `play_cues` · 비교(`compare_drafts` · `adopt_draft`) · 실험 · 가져온 본문은 기록하지 않는다. 그 본문에는 앞 기록이 남아 `matches` 가 거짓이 된다
- 고침 규칙은 호출자가 건 뒤의 본문을 `sent.keep` 에 넘기므로 기록의 지문(`pipeline.text_basis`)이 저장 본문과 맞는다

### `canon/settings.py`

- 사용자 설정(LLM 프로바이더, 모델, API 키, 로컬 서버, 단계별 백엔드)
- 웹 설정 화면에서 저장하면 `~/.canon/config.json` 에 들어간다(`CANON_CONFIG` 로 경로 변경)
- `_write` 는 `store.write_atomic(mode=0o600, fsync=True)` 로 쓴다. 키가 든 임시 파일도 처음부터 본인만 읽고, 쓰다 멈춰도 옛 설정이 그대로 남는다
- 읽고-고치고-쓰는 곳(`update` · `save_preset` · `delete_preset` · `set_prices` · `mark_gemini_cache_unsupported` · `reset_broken`)은 프로세스 안 잠금 `_CONFIG_LOCK`(RLock)을 잡는다. 겹친 단계 칸 PUT 이 서로의 값을 지우지 않는다
- CLI 와 서버처럼 다른 프로세스가 함께 쓰는 경우는 이 잠금이 막지 않는다
- `_load()` 는 (설정, 문제)를 돌려준다. 문제는 `""` · `"corrupt"`(JSON 이 아니거나 객체가 아님) · `"unreadable"`(권한 · 입출력 오류)이다
- 읽지 못한 파일은 권한을 고치면 키가 돌아올 수 있어 보관하지 않고, 쓰기는 권한을 확인하라는 `ConfigBroken` 으로 막는다
- 깨진 파일을 처음 만나면 원문을 `config.json.corrupt-<시각>` 로 한 번 복사한다(0o600, `_keep_broken`). 같은 내용의 보관본이 있으면 새로 만들지 않는다
- 보관본을 쓰다 실패하면(디스크 가득 등) 반쪽 파일을 지우고, 같은 내용은 다시 시도하지 않는다(`_backup_failed`)
- 깨진 동안 읽는 쪽은 `{}`(기본값)를 쓰고, 쓰는 쪽(`_load_for_write`)은 보관본 이름을 적은 `ConfigBroken`(ValueError) 을 낸다. 웹은 409 와 `code: config_broken` 으로 답한다
- `reset_broken` 은 깨진 파일만 빈 설정으로 바꾸고 보관본은 둔다(`POST /api/config/reset`, 설정 화면 '기본값으로 새로 시작'). 깨지지 않은 파일이면 ValueError
- 읽지 못한 파일이면 `reset_broken` 은 ValueError 로 거절한다
- `public()` 의 `config_broken` · `config_backup` 은 깨졌는지와 보관본 경로다. 키 값은 오류 · 로그 · 화면에 찍지 않는다
- `public()` 의 `config_unreadable` 은 읽지 못했는지다(그때 `config_broken` 도 참)
- 환경 변수가 있으면 파일보다 우선한다
- 단계 이름 목록은 `STAGES`
- 스토리보드 · 큐 시트 단계 `board` 는 따로 정하지 않으면 계획 단계를 따른다(`STAGE_PARENT`). 웹 쓰기 작업 · 스토리보드 · 큐 시트 작업과 자동 집필이 이 단계로 부른다
- 상태 변경안 누락 검사 단계 `audit` 는 따로 정하지 않으면 상태 변경안 단계를 따른다. 기본 프리셋은 싼 모델(flash · haiku)을 둔다
- 단계별 환경 변수 이름은 `stage_env`
- 기본 모델은 `DEFAULT_MODEL`
- 작품별 단계 프리셋은 `project_preset` · `stage_provider` · `stage_model`
- 단계별 추론 강도는 `stage_effort`(설정 파일 `stage_efforts`, `CANON_EFFORT_<단계>`)
- 백엔드에 넘길 강도는 `provider_effort`(Claude `EFFORTS`, Gemini `GEMINI_EFFORTS`, Gemini 는 xhigh · max 를 high 로)
- Gemini 명시 캐시를 쓸 곳은 `gemini_cache`(설정 파일 `gemini_cache`, `CANON_GEMINI_CACHE`). agent(기본, 플롯 대화 단계만) | off
- 명시 캐시를 받지 않는 모델은 설정 파일 `gemini_cache_unsupported` 에 남는다(`gemini_cache_unsupported` · `mark_gemini_cache_unsupported`, 적는 쪽은 `llm.GeminiLLM`)
- `mark_gemini_cache_unsupported` 는 설정 파일이 깨진 JSON 이면 적지 않는다(다른 설정을 지우지 않게)
- `public()` 의 `gemini_cache_unsupported` 는 지금 Gemini 연결 방식에서 명시 캐시를 받지 않는 모델 이름 목록이다(설정 화면 모델 칸 안내)

### `canon/static/regexrules.js`

- 규칙 묶음 화면(`#/rules`, 작품 밖, 서버 `regexrules.py` · `routes/regexrules.py`)
- `index.html` 은 `style.js` 바로 뒤에서 이 파일을 읽는다. 읽을 때 바로 부르는 곳은 없다
- 목록 `viewRuleList`: 묶음 이름, 경고 · 고침 · 내보내기 수(`ruleCounts`), 켠 작품 수
- 편집 `viewRuleBundle`(`#/rules/new` · `#/rules/<id>`, 불러오기 `ruleLoad`): 규칙마다 카드 하나(`ruleCard`)
- 규칙 카드는 이름 · 찾을 정규식 · 바꿀 글 · 플래그 · 경고/고침 · 쓴 본문/내보내기 · 켬과 빼기 · 위아래 옮기기를 둔다. 더하기는 `ruleAdd`
- 새 규칙은 화면에서 8자리 id 를 정한다(`ruleBlank`). 저장 몸통(`ruleBody`)은 규칙마다 id 를 그대로 보낸다
- 종류를 내보내기로 고르면 동작을 고침으로 두고 경고를 막는다(서버 검사와 같다)
- 내보내기 규칙의 카드는 '경고' 단추를 꺼 둔다. `ruleSet` 도 내보내기 규칙을 경고로 바꾸지 않는다
- 저장하지 않은 편집은 `S.ruleDirty` 다. 저장 띠 대신 '저장하지 않은 변경이 있어요'(`#rx-dirty`)와 '저장 전으로 되돌리기' 를 둔다
- 저장이 400 이면 서버가 준 이유 줄을 편집 칸에 보인다. 알림(`notices`)은 마지막 저장 응답의 것이다
- 시험 칸 `ruleTestCard`: 붙여 넣은 글이나 작품의 한 화에 지금 칸의 규칙을 걸어 바뀐 곳과 걸린 곳을 보인다(`POST /api/rules/test`, 저장 안 함)
- 버전 칸 `ruleVersionsCard` 와 '이 버전으로 되돌리기' 는 문체 라이브러리와 같은 모양이다
- 다른 화면이 쓰는 순수 함수: `ruleRunSay`(걸기 한 번의 알림 문장) · `ruledLine`(바뀐 곳 수와 규칙 이름) · `ruleSkipSay`(건너뜀 알림)
- 그 화면들(`write.js` · `rewrite.js` · `passage.js` · `convert.js` · `settings.js`)은 이 파일의 함수를 `typeof … === 'function'` 으로 확인하고 부른다. 일부 파일만 읽는 JS 시험이 있다
- 집필 화면 알림 `ruleRunsNote(n, can)`: 아직 되돌리지 않은 곳이 있는 걸기마다 접은 '규칙으로 N곳 고쳤어요'(최근 것 먼저)
- 알림을 펴면 바뀐 곳마다 규칙 이름 · 전 → 뒤 · '되돌리기' 가 있다. 되돌린 곳은 '되돌림' 표시로 남는다
- 아직 되돌리지 않은 곳이 둘 이상이면 '모두 되돌리기'(묻고 함)가 있고, 남긴 곳이 있으면 그 수를 알린다
- 곳 하나를 되돌린 뒤에도 알림을 편 채 둔다(`S.ruleRunOpen`)
- 마지막 걸기가 건너뛰었으면 '규칙 묶음 ○○을 거는 데 너무 오래 걸려서 건너뛰었어요' 를 보인다
- `can` 이 거짓(자동 집필 중 · 고칠 수 없는 화)이면 되돌리기 버튼 없이 보기만 한다
- 되돌리기 전에 저장하지 않은 본문 수정이 있으면 묻고 먼저 저장한다(`ruleUndoRun`). 서버는 저장된 본문을 되돌린다
- 시험은 `tests/test_regexrules_js.py`

### `canon/store.py`

- `projects/<이름>/project.json` 저장

- 저장 전 직전 판을 `project.prev.json` 으로, 시간마다 첫 저장 직전 판을 `backups/project.<날짜-시>.json` 으로 남긴다(하드 링크라 복사하지 않음)

- `backup_list` 는 시간별 · 직전 판 · `before-delete-<화>.json` · `before-serial.json` · 되돌리기 전 판을 새것부터 준다(UTC 시각 · 화 수 · 반영한 마지막 화, 판마다 기억)
- `save_backup`(장편 전환 · 화 지우기 직전 판)은 바꿔치기로 쓰고 fsync 한다. 쓰다 멈춰도 옛 백업이 남는다
- `restore_backup` 은 `backup_list` 의 id 만 받는다. 지금 판을 `backups/before-restore.<시각>.json`(최근 `RESTORE_KEEP` 개)으로 남긴 뒤 저장한다
- `backups/` 안 판의 스냅샷 파일은 작품 폴더의 `snapshots/` 에서 읽는다(`read_disk` 의 `home`)
- 갈래 · 복제 · 플레이 사본은 `backups/` 를 옮기지 않는다(`branches.COPY_SKIP`)
- 작품 캐시: 같은 판이면 검증을 건너뜀. `load_view` 는 캐시 것(고치지 않음, 웹은 `web._view`), `load` 는 깊은 복사본. 저장하면 저장한 내용을 바로 캐시에 둠(`_remember`)
- `peek` 은 작품 목록 카드용 가벼운 읽기다. 캐시에 같은 판이 있으면 그것, 없으면 스냅샷 파일 없이 project.json 만 검증하고 캐시에 두지 않는다
- 파일 판(`tag`, 작품 GET 의 ETag). 웹 요청이 저장한 판은 `saved` 에 남아 응답의 `X-Project-ETag` 가 된다
- 스냅샷은 `snapshots/<화>-<내용 해시>.json` 에 하나씩 두고 project.json 맨 앞 `snapshot_files` 가 차례대로 적는다(`read_disk`). 옛 project.json 안의 스냅샷도 읽는다
- 지난 저장과 같은 스냅샷은 다시 직렬화하지 않는다(`_snap_written`). 어느 판(project.json · prev · backups)도 적지 않은 스냅샷 파일은 지운다
- `backups/` 의 모든 `.json`(되돌리기 전 판 포함)이 적은 스냅샷 파일을 남긴다
- 아무 판도 적지 않아도 `SNAP_GRACE`(60초) 안에 쓴 스냅샷 파일은 지우지 않는다
- `_snap_refs` 는 판의 스냅샷 목록을 돌려준다. 옛 모양이면 None, 없는 파일이면 빈 목록이다
- 판을 읽지 못하면(OSError, 빈 파일, JSON 객체가 아닌 머리, 앞 64KB 안에서 닫히지 않는 목록) `_snap_refs` 가 `SnapRefsUnreadable` 을 낸다
- 판 하나라도 읽지 못하면 `_drop_old_snapshots` 는 그 차례 정리를 건너뛰고 `canon` 로그에 경고를 남긴다
- 판을 계속 읽지 못하면 `snapshots/` 가 커진다
- 읽지 못한 `backups/` 파일이 시간별 · 되돌리기 전 이름(`_HOURLY` · `_RESTORE`)이 아니면 `_drop_old_snapshots` 는 그 파일을 넘기고 정리를 이어 간다
- `save` 는 판 기록 읽기부터 옛 스냅샷 지우기까지 작품 폴더의 `.lock` 에 `fcntl.flock` 을 잡는다(`_disk_lock`). 명령줄과 웹 서버가 함께 저장해도 서로의 새 스냅샷 파일을 지우지 않는다
- 읽고 고쳐 저장하는 구간 전체의 프로세스 사이 잠금은 `jobs.project_lock`(`.edit.lock`)이 맡는다
- `write_atomic` 은 pid · 스레드 id 가 붙은 tmp 파일에 다 쓴 뒤 `os.replace` 로 바꿔 넣고, 바꾸기 직전 tmp 의 stat(판)을 돌려준다
- `write_atomic` 은 글(utf-8)과 바이트(올린 지도 그림)를 함께 받는다
- 덧붙이는 기록 파일(`usage` · research · 비교 `log.jsonl` · soelab 표시)은 바꿔치기하지 않고 `open("a")` 로 덧붙인다
- `write_atomic` 을 쓰는 곳: store · settings · refs · library · studio · autorun · revlab · soelab · research 비교본 · maps/layout · maps/makers · routes/atlas · cli
- `_hold` 는 하드 링크로 남기므로 `write_atomic` 대신 자기 tmp 와 `os.replace` 를 쓴다
- `write_atomic` 의 `mode` 는 tmp 를 처음부터 그 권한으로 만든다. `fsync` 는 내용과 폴더를 디스크에 내린다
- fsync 는 project.json · 스냅샷 파일 · `save_backup` · 설정 파일에만 켠다(3MB 에 1.4ms 쯤). 내보낸 본문 `episodes/*.md` 와 pending · 갈래 · 플레이 · 큐 시트 실험은 바꿔치기만 한다
- 화면 저장 기록(`writer`, `edit_rev` · `saved_by`, 파일 끝만 읽음)
- 파일 끝에서 두 칸을 찾지 못하면 파일 전체를 읽는다. 두 칸은 `Project` 의 마지막 필드여야 한다(`tests/test_store_backup.py`)
- 검토를 기다리는 AI 결과와 실패한 작업(`pending.json`, `load_pending` / `edit_pending`)
- 상태 변경안 결과(`state:<화>`)는 작가가 고르던 체크와 고친 변경안을 `draft` 칸에 함께 둔다
- 결과를 지우거나 새 결과로 바꾸면 초안도 사라진다
- 화 번호로 이름 붙인 바깥 파일(큐 시트 실험 `cuelab/<화>.json` · 블라인드 비교본 `compare/<화>/`, `compare_dir`)은 화를 넣고 뺄 때 `renumber_side_files` 로 옮긴다
- 보낸 프롬프트 기록 `sent/<화>.json.gz`(`sent_path`, `canon/sent.py`)도 같은 바깥 파일이다(`side_files` 의 종류 `sent`)
- 바깥 파일을 `removed/` 로 옮길 때 화 번호 뒤 확장자(`.json` · `.json.gz`)를 그대로 둔다(`_ext`)
- `set_aside_side(name, kind, n)` 는 화를 남기고 본문만 지울 때 한 종류의 바깥 파일을 `removed/` 로 옮긴다
- `renumber_side_files` 는 옮길 파일을 임시 이름(`.renum-<화>`)으로 먼저 옮겨 서로 덮지 않고, 큐 시트 실험 안의 `episode` 도 새 번호로 고친다
- 뺀 화(`gone`)의 바깥 파일은 지우지 않고 `cuelab/removed/` · `compare/removed/` 에 `<화>.<시각>` 으로 남긴다(`SIDE_REMOVED`)
- `renumber_side_files` 에 `aside` 목록을 주면 뺀 화의 파일을 남긴 경로(작품 폴더 기준)를 더한다
- `restore_side_files` 는 그 경로의 파일을 n화 자리로 되돌린다. 그 자리에 파일이 있으면 덮지 않고, `<종류>/removed/<이름>` 꼴이 아닌 경로는 건너뛴다

### `canon/updater.py`

- 코드 자동 업데이트
- `origin/main` fast-forward
- 의존성 설치(`requirements.lock` 이 있으면 그것대로)
- 다시 시작하기 전에 새 프로세스에서 `canon.web` 을 불러 보고, 불러지지 않으면 이전 커밋으로 돌린다(`_smoke`)
- 프로세스 재시작
- `serve` 가 시작 때와 주기적으로 부른다
- 받은 뒤 `web._drain` 이 요청 · 작업이 끝나기를 기다린다. `jobs.DRAIN_LIMIT`(30분)을 넘기면 로그를 남기고 그대로 다시 시작한다
- `serve` 의 감시 스레드(`watch_safely`)는 확인 중 오류가 나도 로그를 남기고 감시를 이어 간다
- `POST /api/update/check`(머지 때 GitHub Actions `notify-server.yml`)는 `wake` 로 바로 부르게 한다

### `canon/web.py`

- 웹 UI 서버(`python -m canon serve`)
- 작품 저장(PUT · PATCH)은 단편 열 계획을 1화부터 끝 화까지 맞춘다(`heatplan.fit` · `fit_turn`). 화수를 바꿔도 빈틈이 생기지 않는다
- 장편은 아크마다 그 아크 범위로 열 계획을 맞춘다. 다음 아크 적용(`/arcs/apply`)은 판돈이 든 제안(`HeatArcProposal`)도 받는다
- 작업 `heat`(`_job_heat`): 이미 있는 기승전결 · 아크 위 열 계획 제안. 결과는 검토를 기다리는 결과(`PENDING_KINDS`)로 남는다
- 작업 `offscreen`(`_job_offscreen`, 계획 단계 모델): 화면 밖 근황 제안. 결과는 `PENDING_KINDS` 로 남는다
- 화면 밖 근황 저장 `POST …/offscreen`(`OffscreenSet`, 고른 인물만) · 지우기 `DELETE …/offscreen/{인물 id}`. 장편에서만 받는다
- 문체 라이브러리 분석 작업 `POST /api/styles/analyze/job`(kind `lib_style`, project `LIB_JOBS` = `.styles`)
- 맨 바깥 미들웨어 `_guard_host` 는 Host 가 IP 주소 · localhost · `*.ts.net` · 이 컴퓨터 이름 · `CANON_ALLOWED_HOSTS` 의 이름이 아니면 403 으로 막는다(DNS 리바인딩)
- `_guard_host` 는 POST · PUT · PATCH · DELETE 에 Origin 이 있으면 그 이름이 Host 나 X-Forwarded-Host 와 같아야 받는다(CSRF). Origin 이 없는 요청(명령줄 · curl)은 받는다
- 작품 문체 분석은 작업 `style`(`_job_style`, `JobIn.text` 200자 이상): 프로필과 원문 전체 기준 지표를 돌려주고 결과는 pending 에 남는다(`PENDING_KINDS`). 옛 `POST …/style` 은 그대로 둔다
- 결과 지우기 `DELETE …/pending/{key}?id=` 는 id 가 같을 때만 지운다. 화면이 옛 결과를 반영하는 사이 같은 키에 새 결과가 들어왔으면 남긴다(`syncPending` 이 id 를 보낸다)
- 작품 카드 `setup_ready`: 설정 도우미 필수 칸이 다 찼는지(`_setup_ready`, setup.js `setupReqs` 와 같은 규칙)
- `/api/config/health` 는 Claude 단계가 있으면 `claude_api`(Anthropic 키 유무)와 `claude` · `claude_message`(구독 설치 · 로그인, `claude.status` 를 60초 기억)를 싣는다. 설정 저장은 기억을 지우고, `/api/claude/status` 는 새로 읽은 값으로 바꾸고, error 는 기억하지 않는다
- 키 없음(`MissingKey`) 답의 문구는 낸 백엔드의 것(Gemini · Vertex · Anthropic)을 쓴다
- 대화 세션 칸만 바꾸는 요청(세션 만들기 · 이름 · 대상 · 권한 모드 · 보관, `_session_edit`)은 화면 저장으로 치지 않는다(`store.writer` 를 비움). 저장하지 않은 변경이 있는 탭의 다음 저장이 다른 탭과의 충돌(409)을 그대로 받는다
- 기능별 라우트 아홉 묶음은 `canon/routes/` 에 있다(`ROUTES`: 문단 연습장 · 프롬프트 놀이터 · 레퍼런스 · 지도 · 역설계 · 쇠맛 · 플레이 · 연구 · 규칙 묶음). 맨 끝의 `_attach_routes` 가 붙인다
- 붙인 라우트는 `app.routes` 에 감싼 모양으로만 들어가서, 응답 모양을 바꾸는 코드는 `_ROUTERS` 의 라우트도 함께 본다(`_SNAPSHOT_LIGHT`)
- `serve` 는 로깅 설정이 없으면 INFO 수준, 시각 · 수준 · 로거 이름을 붙인 형식으로 정한다. 업데이트 · 자동 집필 이어 가기 안내도 이 로그로 낸다
- 작품 GET 과 작품을 돌려주는 응답은 스냅샷을 화 번호만 보낸다(`_SNAPSHOT_LIGHT`). 작품 저장(PUT)은 디스크 스냅샷을 지킨다
- 작품 GET 200 은 화를 뺀 나머지의 판(`_rest_tag`)을 `X-Project-Rest` 로 붙인다
- 저장 응답도 `X-Project-ETag` 와 함께 같은 판을 `X-Project-Rest` 로 붙인다. 그사이 다른 저장이 끼었으면 붙이지 않는다(`_saved_rest`)
- 나머지 판은 작품마다 마지막 파일 판 하나로 기억한다(`_rests`). 저장 응답 · 작품 GET · 화 GET 이 한 번만 계산한다
- `GET /api/projects/{name}/episodes?nums=3,4` 는 고른 화와 `etag` · `edit_rev` · `saved_by` · 나머지 판(`rest`) · 모든 화 번호(`numbers`)만 돌려준다(`get_episodes`, 50화까지)
- `GET /` 는 index.html 의 `/static/*.js` 태그를 내용 해시가 붙은 묶음 하나(`/bundle/<해시>.js`, 오래 캐시)로 바꿔 보낸다(`_bundle`). 파일을 고치면 해시가 바뀐다
- 화면의 작품 저장은 `PATCH /api/projects/{name}`(`ProjectPatch`): 바뀐 최상위 칸만 받고 보내지 않은 칸은 디스크 것을 쓴다. 그 뒤는 `put_project` 와 같다
- 작품 저장(PUT · PATCH)은 지금 상태를 고친 기록(`state_log`)을 디스크 것으로 둔다. 그 기록은 `PUT /api/projects/{name}/state/{cid}`(`state_set`, `stateedit.set_state`)만 고친다
- `state_set` 은 자동 집필이 도는 중이면 막고(`_not_auto`), 프로젝트 잠금 안에서 읽고 저장한다
- PATCH 의 `episodes` 에서 `{"$same": 화}` 는 디스크의 그 화다. 디스크에 없는 화면 409
- 작품 저장(PUT · PATCH)은 디스크 읽기 · `edit_rev` 충돌 검사 · 디스크 칸 지키기 · 저장을 한 번의 `jobs.project_lock` 안에서 한다(`_put_locked` · `_patch_locked`)
- 잠금은 재진입하지 않는다. 잠금을 잡은 채 저장하는 코드는 `_save` 대신 `_save_locked` 를 부른다
- 작품 저장(PUT · PATCH)은 디스크에도 있는 화의 `JOB_EP_FIELDS` 칸(검수 결과 · 흡입력 판정 · 다시 맞추기 표시 · 고칠 곳 · 장면 연출)을 디스크 값으로 둔다(`_keep_job_fields`)
- 작업이나 전용 엔드포인트만 쓰는 화의 칸을 새로 만들면 `JOB_EP_FIELDS` 에 더한다. 그래야 작업 전에 읽은 화면의 저장이 작업 결과를 덮지 않는다
- 아크의 작가 연출 지시(`StoryArc.direction`)도 같은 번호의 아크면 디스크 값으로 둔다(`_keep_job_fields`)
- 작가 연출 지시 `PUT …/episodes/{n}/direction`(`DirectionBody`: episode, arc 는 null 이면 그대로)은 그 화와 그 화가 든 아크(장편만)에 쓴다. 자동 집필 · 그 화를 맡은 AI 작업이 돌면 막는다
- 작품 저장(PUT · PATCH)이 디스크에서 본문이 있는 화를 빼면 디스크 화를 통째로 되돌리고 `X-Canon-Kept` 에 `{"field": "episode", "ep": n}` 로 알린다(`_keep_texts`)
- 작품 저장(PUT · PATCH)이 본문이 있던 화의 본문을 빈 글로 보내면 그 화도 디스크 것으로 통째로 되돌리고 `{"field": "text", "ep": n}` 로 알린다(`_keep_texts`)
- 본문만 되돌리지 않는 까닭: 화면이 보낸 옛 상태(confirmed)가 남으면 본문이 있는데 안 쓴 화로 보여 플롯 잠금이 풀리고 다시 쓰기가 본문을 덮는다
- 되돌린 화도 줄기 표시(`LOCKED_FREE`)는 화면 것을 받고, 이번 저장이 지운 인물 · 줄기는 플롯에서 뺀다(`_restored`). 되돌림이 저장 검사 뒤에 오기 때문이다
- 빠진 화의 본문이 화면이 보낸 다른 화의 본문과 같으면 되돌리지 않는다. 화 끼워 넣기로 번호가 밀린 옛 탭의 덮어쓰기가 끝 화를 겹쳐 남기지 않게 한다
- 본문을 비운 화도 같다. 화 지우기로 본문이 앞으로 당겨진 뒤 옛 탭이 덮어써도 같은 본문이 두 화에 생기지 않는다
- 총 화수(`meta.target_episodes`) 밖의 화를 되돌리면 `"why": "over_target"` 을 붙인다
- 이 본문 지키기는 `force` 로도 풀지 않는다. 화 빼기 · 지우기는 전용 라우트(`remove_episode` · `delete_episode`)가 한다
- 인물 · 떡밥 · 비밀 목록이 비는 저장은 막지 않는다. 작가가 일부러 지운 결과다
- 인물 · 관계도와 지도 응답은 작품 판으로 JSON 을 기억하고 ETag 를 붙인다(`_json_view`)
- CLI 와 같은 store · pipeline · prompts 를 쓰고 화면은 `canon/static/` 의 정적 파일이다
- 컨텍스트 보기 `GET …/episodes/{n}/context` 는 본문 쓰기 요청과 같은 조각(`prompts.episode_parts`)에서 블록마다 한 줄을 만든다
- 보기 인자(`_view_args`): 스토리보드가 있으면 넣고, 큐 시트가 있고 건너뛰지 않았으면(`skipped`) 넣는다. 여는 방식은 비우고 작가 연출 지시는 넣는다
- 보기 줄은 `{id, title, chars, tokens, on, locked, toggle, front, note, budgets, items, dropped, text}` 다. `title` · `chars` 는 옛 화면을 위해 남긴다
- 보기는 같은 블록의 조각을 차례대로 한 줄로 합치고 빈 블록은 뺀다. `tokens` 는 `context.est_tokens` 추정이다
- 보기의 `items` · `dropped` 는 조립에 넘긴 `context.Trace` 에서 온다(넣은 항목 · 뺀 항목과 이유)
- 장편에서 작가가 끈 블록은 보기에 `on: false` · 글자 0 · 빈 글로 들어간다. 단편은 `budgets` 가 빈 목록이다
- 끈 블록의 자리는 블록을 모두 켰을 때(예산은 그대로) 요청에 놓일 자리다(`_all_on_order`). 끄고 켜도 줄이 옮겨 다니지 않는다
- 보기 줄과 `GET …/blocks` 의 `title` 은 `prompts.block_title` 이다
