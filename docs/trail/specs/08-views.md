# 08. 보는 눈: 쌓기와 기획 블록

상태: 끝 (8-1 #583 · 8-2 #584 · 8-3 #585, 2026-11-18). 8-0 시험: hydrogen 먼 화 판만 갈림 ([README.md](../README.md) 1-8) · 계획: [plan.md](../plan.md) 의 8번 · 먼저: 3

## 목표

인물이 상대를 어떻게 보는지(평가)가 화마다 쌓이고, 다음 화 플롯을 짤 때 기획 모델이 그 흐름을 본다.
작가에게는 상태 승인 화면에 '보는 눈' 줄이 생기고, 플롯 초안의 이어받기 결정(`EpisodePlot.carry`)이 평가의 흐름을 이어 받는다.
레퍼런스에서 본 '앞선 행동에 기대어 상대를 다시 매기고, 낱말을 남긴 채 뜻을 옮기는' 흐름([README.md](../README.md) 1-6)을 따라가려는 일감이다.

따르는 정한 규칙:

- 2026-11-17: 보는 눈을 기록하고 다음 화 기획의 재료로 먼저 쓴다. 인물 화면 · 쓰기 · 검수는 그 뒤에 본다.
- 2026-11-17: 쓰기 요청에는 자취 · 보는 눈 블록을 따로 넣지 않는다. 쓰기는 플롯의 이어받기 결정으로만 닿는다.

이 명세는 예전 일감 8(기획 블록) 가운데 보는 눈 몫이다.
보는 눈만으로 처음부터 끝까지 쓸 수 있게, 일감 5 · 6 의 보는 눈 몫(스키마 · 거두기)을 이 명세로 옮긴다.
자취 몫(스키마 · 거두기 · 기획 블록)은 5 · 6 · 9 에 남는다.

## 정할 것

1. 시험부터 할지 — 추천: 8-0 시험을 먼저 한다.
   - 일감 2 처럼 코드 전에 몫을 잰다.
   - 1-7 에서 보는 눈을 쓰기 요청에 넣은 판(86화 W)은 '거짓말' 다시 매기기를 내지 못했다. 기획 요청에 넣은 판은 아직 재지 않았다.
   - 다른 안: 시험 없이 8-1 부터 만든다. 보는 눈이 쌓이려면 반영을 여러 화 거쳐야 해서, 만든 뒤에는 몫을 재기까지 오래 걸린다.
2. 옛 작품의 보는 눈 채우기 — 추천: 이 일감에서는 하지 않는다. 8-0 시험은 스크립트가 시험용 사본에만 채운다.
   - 반영된 화에서 거꾸로 뽑는 기능은 plan.md 의 장기 후보(옛 화에서 거꾸로 뽑기)에 보는 눈도 함께 둔다.
   - 그래서 지금 쓰는 작품은 다음 반영부터 쌓인다. 블록이 몫을 하려면 몇 화가 지나야 한다.
3. 기본 체크와 자동 집필 — 추천: 승인 화면에서 기본으로 체크하고, 자동 집필 · `-y` 도 반영한다(README 정할 것 14 의 추천).
   - 까닭: 관계 사건처럼 본문에 드러난 일의 기록이고, 인물 설정을 바꾸지 않는다.
   - 다른 안: 설정 바꾸기처럼 체크하지 않고 자동 집필은 남겨 둔다.
4. 겉말 칸 — 추천: 둔다. 비워도 된다(README 정할 것 14).
5. 근거 자취 칸 — 추천: 8-1 에 칸만 두고 비워 둔다. 자취(일감 5 · 6)가 생기면 그때 채운다.
   - 다른 안: 칸을 빼고 일감 5 에서 더한다. 그러면 옛 데이터에 칸을 늦게 더하게 된다(기본값이 있으니 읽기는 된다).
6. 블록 예산 — 추천: `plan_views` 1,500자.
   - 근거: `plan_stages` 와 같다. 1-6 꼴의 한 쌍(평가 4개 × 약 40자 + 머리) 약 250자, 주역 쌍 위주 5~6 쌍.
7. 대화 에이전트 — 추천: 이 일감에서는 읽기만 한다. 에이전트가 보는 눈을 쓰는 길은 만들지 않는다.

## 8-0 시험

- 스크립트: `reports/trail-views-<날짜>/` 아래(커밋하지 않음). 1-7 의 `expV2.py` 를 잇는다.
- 대목: 1-7 의 레퍼런스 18화 · 86화, `nsfw_saintess` 사본 89화(엘렌 · 세실리아). 작품은 임시 `CANON_HOME` 사본만 쓴다.
- 보는 눈 줄 만들기: flash 가 대목 앞 화 본문에서 시점 인물의 평가를 뽑고, 사람이 고친다. 한 쌍에 4줄 안팎, 3-5 의 블록 꼴 그대로.
- 판: V(지금 기획 요청, carry 칸 있음) · E(V + 보는 눈 블록). 같은 대목마다 판당 3번.
- 판마다 기획이 고른 carry 로 본문을 한 번씩 쓴다(flash).
- 잴 것(사람이 매김, 한 사람):
  - carry 가운데 '상대를 다시 보는' 줄의 수. 실제 생성에서 flash 는 0/2, hydrogen 은 1/2 였다(2026-11-18).
  - carry 의 뜻이 보는 눈의 흐름에서 다음 걸음인지(같은 평가 되풀이 · 흐름과 어긋남 · 다음 걸음).
  - 본문에서 앞 화 일로 상대를 다시 매기는 속말 문장 수(1-7 과 같은 셈).
  - 보는 눈 낱말이 본문에 그대로 옮겨진 수.
- 판정: E 가 V 보다 '상대를 다시 보는' 줄과 다시 매기는 속말이 함께 뚜렷이 많으면 8-1 로 간다. 갈리지 않으면 멈춘다.
- 결과는 [README.md](../README.md) 1-7 뒤에 새 절로 옮긴다.

## 데이터 · 스키마

```python
class CharView(BaseModel):          # Project.views 의 한 줄. 프로그램이 저장한다
    viewer: str                     # 보는 사람 인물 id
    target: str                     # 대상 인물 id
    episode: int                    # 이 평가가 본문에 드러난 화
    verdict: str                    # 보는 사람이 쓰는 낱말 그대로, 30자 안팎
    surface: str = ""               # 겉으로 다르게 말하면 그 말. 같으면 빈 글
    basis: list[str] = []           # 근거 자취 id. 일감 5 전에는 늘 빈 목록

class ViewChange(BaseModel):        # StateDelta.views 의 한 줄. LLM 이 채운다
    viewer: str
    target: str
    verdict: str
    surface: str = ""
```

- `Project.views: list[CharView] = []`. 옛 `project.json` 은 고치지 않고 읽힌다.
- `StateDelta.views: list[ViewChange] = []`. 설명: '이번 화 본문에서 평가가 새로 드러나거나 바뀐 방향만. 같은 평가가 이어지면 적지 않는다. 대부분의 화는 비어 있다'.
- `ViewChange` 에는 화 번호가 없다. 반영할 때 그 화 번호를 붙인다.
- `basis` 는 `ViewChange` 에 두지 않는다. 일감 5 · 6 에서 자취 id 를 고를 수 있게 되면 더한다.
- dict 칸은 없다(`tests/test_schema_nodict.py`).
- 빈 `views` 는 저장 파일에서 키를 뺄지 정하지 않았다. 다른 목록 칸과 같게 둔다.

## 규칙

거두기(8-2):

- 본문에 드러난 것(속말 · 대사 · 행동)만 적는다. 시점 밖 인물의 속을 짐작해 적지 않는다. 이 문장은 응답 형식 설명에 둔다.
- 같은 방향 쌍의 가장 최근 평가와 글이 같으면 반영하지 않는다(프로그램이 거른다).
- 보는 사람과 대상은 인물 목록의 id 여야 한다. 아니면 버리고 경고를 적는다.
- 상태 변경안 요청의 '지금 보는 눈' 블록은 이번 화 플롯 인물끼리의 방향 쌍마다 최근 평가 1개만 넣는다. 예산은 `plan_views` 를 같이 쓴다.
- 승인: 정할 것 3 을 따른다.
- 되돌리기: 반영 취소는 그 반영이 더한 줄만 뺀다. 작가가 고치거나 지운 줄은 다시 놓지 않는다.
- 인물을 지우면 그 인물이 보는 사람이나 대상인 줄을 지운다.
- 화를 끼워 넣거나 빼서 화 번호가 옮겨지면 `episode` 도 옮긴다.

기획 블록(8-3):

- 넣는 사람: 보는 사람과 대상이 둘 다 그 요청의 기획 인물(`ids`)인 방향 쌍.
- 쌍의 차례: 주역끼리 먼저(`context.core_ids`). 그 안에서는 마지막 평가의 화가 최근인 쌍이 먼저.
- 한 쌍의 줄: 화 차례로 최근 평가 3개. 첫 평가가 빠지면 첫 평가 1개를 맨 앞에 둔다.
- 겉말이 있으면 그 평가 뒤에 '(겉으로는 …)'를 붙인다.
- 예산을 넘으면 뒤 쌍부터 빼고 '(그 밖 n쌍 생략)'을 적는다. 쌍 안의 줄은 자르지 않는다.
- 보는 눈이 없거나 걸린 쌍이 없으면 빈 글이다. 그때 기획 요청 글은 지금과 글자까지 같다.
- 단편(`plot_prompt`)도 같은 블록을 쓴다. 보는 눈이 없는 단편은 요청이 바뀌지 않는다.
- 쓰기 · 검수 · 상태 변경안 요청에는 이 블록을 넣지 않는다(정한 규칙 2026-11-17). 8-2 의 '지금 보는 눈'은 거두기용이고 상태 변경안에만 간다.

## 화면 · 명령줄 · 프롬프트

- 블록 꼴(이름은 예시):

```text
[인물이 서로를 보는 눈 (본문에 드러난 평가의 흐름. 앞이 오래된 것)]
서윤 → 도현: 3화 '뻔뻔한 거짓말쟁이' / 12화 '날 해칠 생각은 없는 사람' / 20화 '다룰 수 있는 사람' (겉으로는 '그냥 아는 사이') / 31화 '내가 감당해야 할 사람'
도현 → 서윤: 5화 '겁먹은 아이' / 28화 '나를 꿰뚫어 보는 사람'
```

- 자리: `serial_plot_prompt` 는 `plan_stage_block` 바로 뒤. `next_arc_prompt` 는 `destination_block` 바로 뒤. `plot_chat_parts` · `plot_prompt` 는 `[관계]` 블록 바로 뒤.
- 화마다 바뀌는 블록이라 `static_context` 뒤에 둔다. 기획 요청은 이미 `[관계]` 가 뒤쪽이라 캐시 순서가 바뀌지 않는다.
- 머리글 밖의 안내 문장은 넣지 않는다. 쓰는 법을 시키는 규칙(몇 화마다 바꾸라 등)을 넣지 않는다.
- `CARRY_DESC` 는 고치지 않는다. '상대를 다시 보게 하는 앞 일을 먼저 본다'가 이미 있다.
- 상태 승인 화면: '보는 눈' 묶음, 줄마다 '서윤 → 도현 · 다룰 수 있는 사람 · 겉으로는 그냥 아는 사이'. 줄은 고칠 수 있다.
- 화면 모양을 바꾸면 `docs/design/` 의 상태 승인 화면 문서를 고친다.
- 고친 뒤 `brief` 출력(작업지시서)을 함께 본다.
- 명령줄 명령 · 웹 엔드포인트는 더하지 않는다. 상태 변경안 · 반영의 기존 길을 쓴다.
