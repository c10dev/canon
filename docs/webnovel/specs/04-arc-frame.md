# 04. 부 · 아크 기획을 이야기 틀별로

상태: 진행 (claude/arc-frame-b29cf1, [#539](https://github.com/c10dev/canon/pull/539)) · 계획: [plan.md](../plan.md) 의 4번 · 먼저: 1, 2

## 목표

웹소설 틀(`Meta.frame = "webnovel"`)을 고른 장편은 부 · 아크 기획 요청이 아크 하나를 보상 루프 한 바퀴(목표 → 짧은 고구마 → 사이다 → 성장)로 짜게 한다.
아크에 '얻는 성장'(`StoryArc.gain`) 칸이 생기고, 하렘 요소(`harem`)를 고른 장편은 '공략 대상'(`StoryArc.focus`) 칸이 생긴다.
드라마 틀(기본)이고 하렘 요소가 없으면 모든 요청 글과 응답 형식이 지금과 글자까지 같다.
이야기 틀이 실제로 기획을 바꾸는 첫 일감이다. [README.md](../README.md) 의 2026-11-14 규칙(틀 · 하렘 요소 · 이 일감의 정할 것 5~7)을 따른다.

## 정할 것

사용자가 2026-11-14 에 plan.md 의 정할 것 5 · 6 · 7 을 추천안으로 진행하라고 했다. 아래 1~3 은 추천안으로 진행한 것이다.

1. 하렘을 틀이 아니라 요소 장르 `harem` 으로 가를까요? — 추천안으로 진행: 그렇다(일감 2 가 요소를 넣었다).
2. 아크마다 공략 대상 칸(`StoryArc.focus`)을 둘까요? — 추천안으로 진행: 둔다.
3. 관계 단계 말을 더할까요? — 추천안으로 진행: 더하지 않는다. 그 뒤 진도는 이정표 라벨과 접촉 사다리로 충분하다고 본다.

아래는 이 일감에서 정하지 않고 남긴 것이다.

4. 하렘 줄을 드라마 틀 작품에도 넣을까요? — 이 일감은 넣는다. 정할 것 1 이 '하렘은 틀이 아니라 요소로 가른다'이고, README 제안이 '하렘은 요소가, 보상 박자는 틀이 가른다'로 축을 나눴기 때문이다. 웹소설 틀 안에서만 켜려면 `prompts.arc_axes` 한 줄을 바꾼다.
5. 웹소설 틀에서 '같은 크기의 갈등을 되풀이하지 않습니다'(부 구성)를 대신할 문장을 둘까요? — 출처가 없어 대체 문장 없이 뺐다. 뜻의 일부(한 단계씩 커짐)는 같은 줄 앞 문장에 남았다.
6. 웹소설 틀의 '갈등' 칸 이름표와 도움말 — 이 일감은 이름표를 바꾸지 않는다. 안: 이름표 '막는 것 (고구마)', 도움말 '이 아크에서 주인공을 잠깐 막는 것. 1~3화로 짧게'. 응답 형식의 conflict 설명은 이미 이 뜻으로 바꿨다.
7. 대화 제안 칩(`static/agent.js` 의 '갈등을 하나 더' · '갈등을 더 개인적인 걸로')을 웹소설 틀에서 바꿀까요? — 이 일감은 두었다. 출처가 있는 대체 문구가 없다.
8. 단편 → 장편 재구성(`rebuild_prompt`)도 틀별로 가를까요? — 이 일감은 두었다(일감 범위에 없음). 재구성 화면에는 두 칸을 두어 작가가 적을 수 있다.
9. 단편 → 장편 전환 · 재구성 응답 형식에 `gain` · `focus` 를 넣을까요? — 넣지 않았다. 전환은 부 구성 줄만 틀별로 가른다. 아크 1 의 두 칸은 전환 화면에서 작가가 적는다.
10. 작가가 직접 적은 '하렘'(장르 id 가 아닌 글)도 하렘 요소로 볼까요? — 이 일감은 장르 안내(`genres.guide`)처럼 id `harem` 만 센다. 사용자 장편 몇 편이 '하렘'을 글로 적어 두었다. 설정 화면에서 요소 '하렘'을 다시 고르면 켜진다.
11. 화별 플롯 · 본문 쓰기 요청에 아크의 `gain` · `focus` 를 넣을까요? — 이 일감은 넣지 않았다. 일감 6 이 화별 플롯 규칙과 함께 정한다.

## 데이터 · 스키마

- `StoryArc.gain: SkipJsonSchema[str] = ""` — 이 아크에서 주인공이 얻는 성장.
- `StoryArc.focus: SkipJsonSchema[str] = ""` — 공략 대상 인물 id 하나.
- `ArcEdit` 에도 같은 두 칸을 둔다(플롯 대화 변경안).
- 옛 `project.json` 은 고치지 않고 읽힌다. 빈 값은 저장 파일 · API · 프롬프트 어디에도 키가 생기지 않는다(`drop_empty_frame_fields`, `StoryArc` · `ArcEdit` 의 직렬화).
- `conflict` 칸은 지우지 않는다. 웹소설 틀의 응답 형식에서 설명만 '이 아크에서 주인공을 잠깐 막는 것 (짧은 고구마, 1~3화)'로 바꾼다.

### 응답 형식: 틀에 따라 다른 형식

- 저장 모델은 두 칸을 응답 형식에서 뺀다(`heat` · `direction` 과 같은 `SkipJsonSchema`).
- 근거: 작업지시서(`brief_parts`)가 응답 형식을 글로 붙인다. 칸을 늘 넣으면 드라마 틀의 `long:brief:arc` · `*:brief:agent_plot` 스냅샷이 바뀐다.
- 웹소설 틀이나 하렘 요소가 있는 장편은 `schema.framed(형식, gain, focus)` 가 만든 판으로 받는다. 판은 원래 형식을 이어받고 이름이 같다.
- 판이 바꾸는 곳은 아크(`StoryArc`) · 아크 변경안(`ArcEdit`) 칸뿐이다. 그 형식을 품은 형식(`ArcProposal` · `HeatArcProposal` · `PlotRevision` · `PlotAgentStep`)은 그 칸의 타입만 바꾼다.
- 둘 다 아니면 `framed` 는 원래 형식을 그대로 돌려준다. 단편은 늘 원래 형식이다(`prompts.arc_axes`).
- 받은 값은 원래 형식의 인스턴스이고, 저장할 때 원래 형식의 칸으로 직렬화된다.

## 규칙

- `focus` 는 있는 인물(인물 · 인물 후보 · 이 아크의 새 인물) id 만 남긴다. 없는 id 는 비운다(`clean_arc` · `_clean_arc_edit` · 전환 · 재구성).
- 이 작품의 응답 형식이 묻지 않은 칸은 플롯 대화가 지우지 않는다(`keep_unasked`): 지금 아크(다음 아크면 초안)의 값을 그대로 둔다. 틀을 드라마식으로 되돌려도 작가가 적은 값이 남는다.
- 틀을 바꿔도 이미 적은 아크 칸은 그대로다. 확정 플롯 · 본문도 그대로다.
- 관계 수치(`dynamics.py`)와 관계 단계 말은 바꾸지 않는다. '관계는 주로 위로만 오릅니다'는 프롬프트 줄일 뿐이다.
- 대화 에이전트는 지금처럼 작가가 고른 권한 모드 안에서 아크 칸을 고친다. 두 칸도 같은 아크 칸 묶음이다.

## 화면 · 명령줄 · 프롬프트

- 아크 카드 · 다음 아크 제안 · 아크 고치기 · 전환 · 재구성 화면에 '얻는 성장' · '공략 대상' 칸.
- 덜기(`docs/design/README.md`): '얻는 성장'은 웹소설 틀이거나 값이 있을 때만, '공략 대상'은 하렘 요소가 있거나 값이 있을 때만 보인다. 드라마 틀 작품의 화면은 늘 보이는 칸이 늘지 않는다.
- 두 칸의 설명은 늘 보이는 글(`hint`)이 아니라 설명 풍선(`help`)이다. 늘 보이는 안내 문장 수는 두 틀 모두 그대로다. 버튼은 더하지 않았다.
- 플롯 대화 변경안의 칸별 비교(`ARC_FIELDS`)는 바뀐 칸만 보이므로 두 칸을 늘 목록에 둔다.
- '갈등' 이름표와 도움말은 그대로 두었다(정할 것 6).
- 설정 화면의 이야기 틀 설명 풍선: '장편의 부와 아크 기획은 이 값을 따라요. 화별 플롯은 아직 따르지 않아요.'
- 명령줄: `nextarc` · `revise` 의 아크 출력에 값이 있을 때만 '얻는 성장:' · '공략 대상:' 줄.
- 블록 자리는 바뀌지 않는다. 틀별 줄은 지금 요구사항 줄 자리에서 갈린다. 새 블록 · 예산은 없다.
- 값이 찬 두 칸은 부 · 아크 기획과 아크 분석 요청(작업지시서 다음 아크 · 대화 에이전트 첫 단계, 플롯 대화 둘, 아크 요약, 영향 분석)에만 들어간다. 빈 값은 키가 생기지 않는다.
- 화별 플롯 · 본문 쓰기 · 검수 · 스토리보드의 '지금 부와 아크'(`structure_text`)에는 두 칸을 넣지 않는다. 그 요청이 두 칸을 어떻게 쓸지는 일감 6 이 정한다(정할 것 11).

- 판마다 한 번씩만 돌렸다. 호출 상한 8회에 닿아 2~3회씩은 채우지 못했다.
- 웹소설 틀에서 `gain` 은 채워졌고(1/1), `payoff` 는 두 틀 모두 있었다(3/3).
- 구간 나눔은 같은 작품에서 두 틀이 같았다(장편 A). 고구마 화수는 아크 제안의 구간으로는 보이지 않는다. 웹소설 판의 conflict 는 이 아크에서 일어나는 사건 하나였고, 드라마 판은 바깥 압박과 주인공의 오랜 상처를 함께 적었다. 이 차이는 한 판 비교라 우연과 가르지 못한다.
- 하렘 작품의 `focus` 는 모델 출력으로 확인하지 못했다. mock 시험(`test_next_arc_webnovel_harem`)과 조립된 요청 · 응답 형식(`long_web:brief:arc`)까지만 확인했다.
- 출력 한도에 걸린 응답(약 5.7만~6.2만 토큰)은 두 틀 모두에서 나왔다(4판 중 3판의 첫 응답). 글과 응답 형식이 바뀌지 않은 드라마 판에서도 나왔다. 원인은 보지 않았다.

## 확인하지 못할 것

- 작가가 웹소설 틀 아크 제안을 받아 플롯과 본문까지 쓴 뒤의 느낌(작가 취향 판단).
- 고구마 화수는 아크 제안만으로 재지 못한다. 화별 플롯이 생겨야 보인다(일감 6 · 7).
- 하렘 작품의 `focus` 모델 출력과 판당 2~3회 반복은 호출 상한에 닿아 재지 못했다. 사용자가 할 단계: 하렘 요소를 고른 장편에서 웹소설 틀로 다음 아크를 두세 번 제안받아 공략 대상이 있는 인물로 오는지 본다.
