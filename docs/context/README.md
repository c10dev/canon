# 컨텍스트 조립 작업 문서

Canon 컨텍스트 조립(매 화 프롬프트에 무엇을 넣고 무엇을 빼는가)을 고치는 일의 설계 자산이다.
이 일은 롤플레이 채팅 프런트엔드 RisuAI 의 생각 몇 가지를 빌려 온다.
빌려 오는 것은 넷이다: 조건부 넣기(활성화), 프롬프트 보기와 블록 설정, 규칙 자동화(정규식 규칙 · 선언형 규칙), 접은 줄거리 고르기.
빌려 온 생각은 Canon 의 구조화 데이터와 승인 흐름으로 옮겨서만 넣는다. RisuAI 의 코드와 기본 프롬프트 글은 가져오지 않는다.
기능이 들어가면 동작 설명은 [DESIGN.md](../../DESIGN.md) 에 쓰고 이 폴더를 가리킨다. 이 폴더는 일을 나누고 이어 가는 데 쓴다.

|---|---|---|
| README.md (이 문서) | 목적, 정한 규칙, 원칙과의 경계, 용어, 넣지 않는 것 | 이 폴더의 일을 시작하기 전 |
| [plan.md](plan.md) | 일감 차례, 먼저 끝날 것, 같이 할 수 있는 묶음 | 다음 일을 고를 때 |
| [compat.md](compat.md) | 1:1 대응표: CCv3 로어북 ↔ 활성화 묶음, RisuAI 정규식 스크립트 ↔ 정규식 규칙, CBS ↔ 매크로 | 필드 이름을 정하거나 바꿀 때 |
| [specs/](specs/) | 일감마다 작업 명세서. 틀은 [specs/TEMPLATE.md](specs/TEMPLATE.md) | 일감을 시작할 때 |

이 폴더를 더하는 변경은 AGENTS.md 의 '언제 무엇을 읽나' 표에도 줄을 더한다: 컨텍스트 조립(활성화 · 블록 설정 · 정규식 규칙 · 선언형 규칙 · 접은 줄거리 고르기)을 고칠 때 → `docs/context/`.

## 원칙과의 경계

AGENTS.md 의 설계 원칙과 이 일이 만나는 곳이다. 명세서는 이 경계를 넘지 않는다.

### 프롬프트 보기와 블록 설정 (B)

- 블록 차례와 블록 글은 `prompts.py` 한 곳에 그대로 둔다. 작품 설정은 블록을 끄고 켜는 값과 블록 예산 값만 가진다.
- API 경로와 작업지시서 경로(`brief`)는 같은 블록 설정을 읽는다. 블록 설정은 `prompts.py` 의 조립 함수 안에서 읽고, 호출부마다 따로 거르지 않는다.
- 블록을 꺼도 남은 블록의 차례는 바뀌지 않는다. 바뀌지 않는 블록이 앞, 화마다 바뀌는 블록이 뒤라는 차례는 그대로다.
- 블록을 끄거나 예산을 바꾸면 그 작품의 캐시 앞부분이 바뀐다. 이것은 작가가 고른 결과다.
- 이번 화 플롯, 문체, 인물의 불변 설정 블록은 끌 수 없다(Q19). 이 셋이 빠지면 '말투와 성격은 고정'이라는 원칙을 지킬 수 없다.
- 인물의 불변 설정은 이번 화 플롯에 나오는 주연 · 조연 · 단역 모두를 뜻한다(Q31).
- 블록 설정은 작가가 넣는 설정이다. AI 출력이 아니므로 승인 흐름을 거치지 않는다. 대화 에이전트는 이 값을 고치지 않는다(Q29).
- `context.BUDGET` 은 주로 장편 경로가 쓴다.
- `BUDGET["deadlines"]` 와 `BUDGET["stage"]` 는 단편 경로에도 걸린다(`timeline.py` · `prompts.py`).
- 플레이 모드는 자기 `play_*` 키를 쓴다.
- `BUDGET` 키는 블록마다가 아니라 호출부마다 있다(예: `facts` · `check_facts` · `plot_facts` · `plan_facts`). 블록 설정과 키의 대응은 정할 것 8 이다.
- 작품마다의 예산은 인자로 넘기거나 `Project` 에서 읽는다. 전역 `context.BUDGET` 에 쓰지 않는다. 자동 집필이 여러 작품을 스레드로 함께 돌리기 때문이다.
- 블록 설정(끄고 켜기 · 예산)은 장편에만 둔다. 단편 경로는 바꾸지 않고 보기만 키운다(Q32).
- 프롬프트를 이미 돌려주는 길목이 있다: `GET /api/projects/{name}/episodes/{n}/prompt`(`web.py`)는 system 과 prompt 를 돌려준다.
- 프롬프트 놀이터(`canon/promptlab.py`)도 Canon 프롬프트를 불러 실제 호출처럼 돌린다.
- 일감 3 이 위 길목을 넓힐지 놀이터를 넓힐지는 명세서 03 에서 정한다. 둘을 겹쳐 새로 만들지 않는다.
- 프롬프트 보기는 읽기 전용이다. 보기 위해 조립하는 일이 작품 데이터를 바꾸지 않는다.

### 규칙 자동화 (C)

- 정규식 규칙과 선언형 규칙은 작가가 쓰거나 적용한 데이터다. AI 출력이 아니다.
- AI 가 규칙을 제안할 수 있다(Q29). 제안은 작가가 적용해야 규칙 묶음에 들어간다.
- 정규식 규칙의 고침은 결정적인 글 바꾸기다. AI 를 부르지 않는다.
- 고침은 작가가 보기 전에 적용하지만 기록을 남기고 되돌릴 수 있다(Q12). 되돌리면 생성된 그대로의 본문으로 돌아간다.
- 정규식 규칙의 경고는 본문을 바꾸지 않는다. 검수 결과와 함께 보인다. `Finding.origin = "rule"` 이 규칙 판정 지적의 앞선 예다(장면 연출 규칙).
- 선언형 규칙은 상태를 바로 쓰지 않는다(Q13). 상태를 바꾸는 효과는 상태 변경안의 제안으로만 승인 화면에 오고, 작가가 적용해야 반영된다.
- 규칙 제안은 기본으로 체크해서 온다(Q22). 작가가 규칙을 직접 쓰고 켰으므로 그 결과를 기본으로 받는다는 뜻이다.
- 자동 집필은 규칙 제안도 사용자가 정한 승인 정책 안에서만 반영한다(Q22).
- 관계 수치는 조건에서 읽기만 한다(Q27). 규칙은 관계 수치를 제안하지 않는다. 관계 수치는 `dynamics.py` 가 사건에서 계산한다는 원칙 그대로다.
- 선언형 규칙의 효과 (x)는 프롬프트에 항목을 넣는 것이다. 이것은 활성화 판정의 조건 하나이므로 판정은 `context.py` 에 둔다(Q7 · Q13).
- 매크로는 값을 읽기만 한다(Q11). 프롬프트를 조립하는 동안 작품 데이터를 바꾸지 않는다.
- LLM 이 채우는 응답 형식에 규칙 · 활성화 필드를 넣을 때 dict 타입 필드를 쓰지 않는다.

### 활성화와 기억 (A · F)

- 활성화 판정은 단편과 장편 모두에 쓰지만, 단편의 기본값은 지금 동작 그대로다(Q18). 기본값을 둔 단편 작품의 프롬프트는 바뀌지 않는다.
- 활성화는 저장된 데이터를 바꾸지 않는다. 무엇을 프롬프트에 넣을지만 고른다(`context.py` 모듈 설명과 같은 원칙).
- 예산을 넘겨 뺀 항목은 몇 개인지와 이름을 남긴다(Q17). '예산을 넘겨 뺐으면 몇 개 뺐는지 적는다'는 원칙을 이름까지 넓힌다.
- 접은 줄거리 고르기는 장편의 `story_so_far` 안에서만 바꾼다(Q18). 단편의 줄거리 블록은 바뀌지 않는다.
- 키워드 제안은 AI 가 하고 적용은 작가가 한다(Q16). 대화 에이전트의 키워드 고치기는 권한 모드와 되돌릴 값 규칙을 따른다(Q29).
- 활성화는 `static_context` 에 들어가는 인물(`static_characters` → `context.core_ids`)을 바꾸지 않는다. 화마다 앞 블록에 넣고 빼면 캐시 앞부분이 깨진다.
- 키워드 활성화는 장편 쓰기 프롬프트의 '아크 동안 그대로인 것' 뒤 블록에만 영향을 준다(`prompts.serial_parts`).
- 접은 줄거리(`story_parts` 의 past)는 `static_context` 바로 뒤, 아크 동안 그대로인 자리에 있다. 화마다 고르면 이 블록이 화마다 바뀌어 캐시가 깨진다(정할 것 9).

### LLM 호출과 시험

- 키워드 AI 제안(일감 4)은 새 LLM 호출이다.
- 대화 에이전트의 정규식 규칙 제안(6b)은 새 LLM 호출이 아니다. 에이전트의 기존 `chat` 호출이 도구 인자를 채운다(2026-11-09, 06b 의 정할 것 3).
- 새 호출은 `get_llm(단계)` 로 부르고 단계 이름은 `settings.STAGES` 에서 고른다. 새 단계를 둘지 있는 단계를 쓸지는 정할 것 10 이다.
- 새 호출은 `usage.record` 로 사용량에 잡힌다.
- 새 기능의 가짜 응답은 `mock_key_suggest.py` 같은 `mock_<기능>.py` 로 둔다.
- 제안 응답 형식에 dict 타입 필드를 쓰지 않는다.
- 새 웹 길목을 더해도 `python scripts/make_openapi.py` 를 돌리지 않는다. Swift 앱 개발이 멈췄기 때문이다.

## 정할 것

폴더 전체에 걸린 질문이다. 일감 하나에 걸린 질문은 그 명세서의 '정할 것'에 쓴다. 정하면 위 '정한 규칙'에 더한다.

1. 블록 끄고 켜기를 단편에도 쓰는가 — 정함(2026-11-08, Q32): 블록 끄고 켜기와 예산 바꾸기 모두 장편에만 둔다. 단편은 보기 강화만 받는다.
2. 블록 설정과 켠 규칙 묶음을 어디에 저장하는가 — 추천: `Project.settings`(`Settings`)에 둔다. `model_preset` 처럼 전역 id 를 가리키고, 지운 묶음은 건너뛴다.
   - 전역 규칙 묶음은 문체 라이브러리(`CANON_STYLES`) 옆의 새 전역 저장 자리에 둔다(예: 환경 변수 `CANON_RULES`).

   - 새 환경 변수는 `tests/conftest.py` 가 지우는 목록에도 더한다.
3. 정규식 규칙의 고침을 어느 자리에 거는가 — 명세서 06 의 정할 것 2 에서 정한다. 추천: `write_episode` · `rewrite_episode` · `polish_episode` · `revise_passage` 가 `ruled` 인자를 받을 때만 건다. `_write` 안에는 걸지 않는다.
   - 까닭: 실험 · 비교 호출자도 `write_episode` 를 부른다. 저장 함수(`replace_text`)에도 걸지 않는다. 자동 집필이 `replace_text` 를 거치지 않기 때문이다.
   - 작업지시서(`brief`) 경로로 바깥 채팅 앱에서 쓴 본문은 웹 본문 길목으로 저장되고 위 함수를 거치지 않는다. 이 본문에 고침을 걸지는 명세서 06 의 정할 것 10 에서 정한다.

5. 선언형 규칙의 효과 (y)가 제안할 수 있는 상태의 범위 — 추천: 상태창 값과 복선 상태만 둔다. 인물 설정 바꾸기(기본 체크 안 함 원칙)와 관계 수치(AI · 규칙이 적지 않음 원칙)는 넣지 않는다.
