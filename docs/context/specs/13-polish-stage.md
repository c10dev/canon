# 13. 퇴고 단계 (집필 요청의 금지 규칙을 쓴 뒤 고치기로 옮김)

상태: 진행 (claude/polish-stage, [#491](https://github.com/c10dev/canon/pull/491)) · 계획: [plan.md](../plan.md) 의 13번 · 먼저: —

## 목표

장편 집필 요청이 '해야 할 것'만 담게 한다.
'하지 말 것'(쇠맛 패턴 상한, 금지 표현, 문장 끝 몫, 되풀이 구절)은 쓴 뒤의 퇴고 호출로 옮긴다.
퇴고 호출은 코드가 본문에서 찾은 자리를 인용해 받고, 그 자리를 고친 판을 새 판 후보(`Episode.candidate`)로 낸다.
작가는 집필 화면의 판 비교에서 고른다.

이 일감은 새 단계를 만들지 않는다.
지금 있는 서술 다듬기(`pipeline.polish_episode`, `prompts.polish_prompt` · `POLISH_RULES`, 가드 `pipeline.polish_problem`, 자동 집필 `Policy.polish`, 다시 생성 방식 `polish`)를 키운다.

2026-11-10 에 작가와 정한 것(앞 세션):

- 퇴고는 검수에 합치지 않고 집필과 검수 사이에 둔다. 판을 바꾸면 검수 결과가 지워지므로 퇴고가 검수보다 먼저다.
- 규칙 층(`Settings.rule_layers`, PR #475)에 `polish` 층을 더한다. 따로 표시를 만들지 않는다.
- 가르는 기준: 쓴 뒤 문장만 고쳐서 해결되면 퇴고로 옮긴다. 장면을 다시 써야 하면 긍정형 문장으로 집필에 남긴다.
- 퇴고 요청에는 코드가 찾은 위반만 넣는다.

단편(`form = "short"`) 경로는 바꾸지 않는다.
켜기 전까지는 장편도 지금과 같다(아래 '데이터 · 스키마'의 `Settings.polish_stage`).

## 정할 것

작가에게 묻는 네 가지다.
추천안을 먼저 쓴다.

1. 손으로 쓸 때의 흐름 — 추천: 퇴고 단계를 켠 작품은 본문 쓰기 작업이 같은 작업에서 퇴고 판을 만들어 새 판 후보로 둔다.
   - 까닭: 퇴고로 옮긴 규칙은 집필 요청에 더는 없다. 퇴고를 건너뛴 초고는 그 규칙을 한 번도 받지 않는다.
   - 까닭: 새 판 후보라 작가가 고르기 전에는 본문이 바뀌지 않는다(승인 원칙).
   - 앞선 꼴: `Settings.check_after_write` 가 '쓴 뒤 같은 작업에서 바로 X' 를 이미 한다.
   - 비용: 화마다 revise 단계 호출이 하나 는다.
   - 다른 안: 버튼만 둔다(지금 '다시 생성 → 서술만 다듬기'). 작가가 누르지 않으면 금지 규칙이 빠진 초고가 그대로 남는다.
   - 쓴 뒤 바로 검수(`check_after_write`)와 함께 켜져 있으면 검수는 하지 않는다. 판을 고르면 검수 결과가 지워지기 때문이다. 화면은 '판을 고른 뒤 검수하세요'를 보인다.
   - 다시 생성(새 판)도 같은 작업에서 퇴고한다. 후보 칸은 하나라 퇴고한 글이 후보가 되고, 퇴고 전 글은 이전 판(`versions`)에 남긴다.
2. `Policy.polish` 기본값 — 추천: 퇴고 단계를 켠 작품에서는 자동 집필이 늘 퇴고한다(체크를 켠 채 잠그고 까닭을 적는다). 켜지 않은 작품은 지금처럼 끔이다.
   - 까닭: 금지 규칙을 뺀 초고를 퇴고 없이 반영하면 그 규칙이 아무 데도 없다.
   - 지금 기본이 끔인 까닭(`docs/modules/core.md` 의 `canon/autorun.py` 절: 호출이 늘고 Gemini 가 자기 글을 다듬은 판이 졌다)은 퇴고 단계를 켜지 않은 작품에 그대로 맞는다.
3. 화면에서 퇴고를 보일 자리 — 추천: 집필 화면의 판 비교(지금 새 판 후보 비교)에 둔다.
   - 비교 머리에 '찾은 자리 n곳' 을 접어 둔 목록으로 붙인다(규칙 이름과 인용 문장, 퇴고 뒤 남은 수).
   - 까닭: 다듬기 판은 이미 `Episode.candidate` 로 집필 화면에 온다. 새 화면을 만들지 않는다(`docs/design/README.md` 의 '덜기').
   - 검수 화면은 퇴고 다음이다. 검수 화면에서 판을 바꾸면 그 화면의 결과가 지워진다.
4. 퇴고 모델 — 추천: 지금처럼 revise 단계 모델(`get_llm("revise")`)을 쓰고, 추천 모델로 Claude 를 적는다. 코드에 제공자를 박지 않는다.
   - 까닭: 실측(2026-11-04)에서 Claude 가 다듬은 판은 이겼고 Gemini 가 자기 글을 다듬은 판은 졌다(DESIGN.md 4장 '서술 다듬기').
   - 까닭: 기본 LLM 은 Gemini 라는 작가 결정(AGENTS.md)을 지킨다. 퇴고 단계를 켤 때 revise 모델이 Gemini 면 안내 한 줄만 보인다.
   - 표적 퇴고(위반 자리를 인용해 줌)는 Gemini 결과를 바꿀 수 있다. 실험에서 Gemini flash 퇴고를 덤 조건으로 잴 수 있다(아래 '실험').

2026-11-10 결과: 작가가 넷 모두 추천안을 골랐다. [README.md](../README.md) 의 정한 규칙에 더했다.

## 1. 규칙 줄마다 둘 자리

'집필' 은 쓰기 시스템 프롬프트(`writer_system` 의 `prose_rules`)나 쓰기 지시문 꼬리에 남는다는 뜻이다.
'퇴고' 는 집필 요청에서 빼고, 퇴고 요청에서 코드가 찾은 위반의 규칙 이름과 문구로만 들어간다는 뜻이다.
'문체 원문' 칸은 문체 원문이 있는 작품(`prompts.styled`)에서 어떻게 되는지다.

- 긍정형 문구는 원문의 대신 할 일을 남기고 금지 절만 뺀 것이다(`docs/prompts/editing.md` 5절). 새 뜻을 더하지 않았다.

- 3번 원문의 금지 절('교훈으로 끝내지 않음')은 '마지막 문장은 행동이나 대사' 가 막는다. 교훈 문장을 찾는 코드는 없어 퇴고로 옮기지 않는다.
- 셋씩 나열의 상한은 규칙 글의 '한 번 이하'를 쓴다. `AI_PATTERNS` 의 경고 상한(2)과 다르다. 규칙 글이 작가가 받아들인 출처다.
- 이 기계의 장편 11편은 모두 문체 원문이 있다(2026-11-10, `projects/` 읽기). 그래서 plain 줄(4 · 7 · 16)은 지금 어느 작품에도 가지 않는다. 실험도 이 줄들을 재지 못한다.

### 1.2 쓰기 지시문 꼬리

| 조각 | 지금 글 | 자리 | 집필에 남는 글 | 퇴고에서 찾는 것 |
|---|---|---|---|---|
| `WRITE_STYLE_LINE` | 문체는 스타일 프로필과 문체 예시 문단을 따르고, banned_phrases 의 표현은 쓰지 않습니다. | 나눔 | 문체는 스타일 프로필과 문체 예시 문단을 따릅니다. | `StyleProfile.banned_phrases` 글자 검사(`metrics.pattern_spans` 의 cliche 갈래, 서술 줄만) |
| `RETOLD_LINE` | 앞 화에서 읽은 설정과 지난 사건은 다시 설명하거나 요약하지 않고(…), | 집필 | 독자가 앞 화에서 읽은 세계관 설정과 지난 사건은 이미 아는 것으로 두고(오랜만에 다시 나오는 인물만 처음 나올 때 한두 문장으로 짚음), | 없음 (다시 설명한 단락을 찾는 코드가 없다) |
| `ending_line` · `ending_rule` | 서술 문장의 끝을 섞습니다. 열에 k쯤만 '~다.'로 … | 퇴고 | — | `measure().da_ending_ratio` 가 `ending_counts` 의 몫을 넘거나, '~다.' 끝이 `ENDING_RUN` 줄 이상 이어진 덩어리 |
| `ECHO_RULE` · `echo_block` | 아래 구절을 그대로 쓰지 않고 다른 말로 씁니다. … | 퇴고 | — | `echoes.recent(p, n)` 의 구절 가운데 이번 본문에 나온 것 |
| `WRITE_SHIFT_LINE` (덤) | emotional_shift 는 감정 이름으로 서술하지 말고 행동과 대사로 보여 줍니다. | 집필 | 플롯의 emotional_shift 는 행동과 대사로 보여 줍니다. | 1번 줄의 '감정 이름 서술'이 함께 잡는다 |
| `WRITE_SPEECH_LINE` (덤) | speech_style 의 대사 예시를 그대로 쓰지 않고 어미 · 호칭 · 길이만 따릅니다. | 집필 (그대로) | — | 없음 (대사 줄은 퇴고가 바꾸지 못한다) |

- 문장 끝 몫을 집필에서 빼는 근거: 쓰기 요청의 몫 줄은 '~다.' 끝 89% → 82% 였고, 다듬기 호출은 85~96% → 65~75% 였다(DESIGN.md '문장 끝 섞기' · '서술 다듬기', 2026-11-04).
- 시점 인물의 서술 말투로 쓰는 화(`prompts.voiced`)는 지금처럼 문장 끝을 집필에도 퇴고에도 넣지 않는다.
- `banned_phrases` 는 스타일 프로필 JSON(`style_rules_view`)에도 있다. 퇴고 단계를 켠 작품은 거기서도 뺀다. 퇴고 층 지킬 것 · 피할 것이 이미 빠지는 것(`layer_rules(p, "write")`)과 같은 길이다.
- 꼬리에서 문장이 빠지므로 `tests/test_write_budget.py` 의 지시 문장 수(지금 mock 장편 12/12, 2026-11-10 잼)가 준다. 긍정형 문구는 모두 시스템 쪽(`_PROSE_RULES`)이나 이미 있는 문장 안에 두어 꼬리 문장을 늘리지 않는다.

### 1.3 함께 바뀌는 경로

- `prose_rules` 는 `writer_system` 과 `reviser_system` 이 함께 쓴다. `reviser_system`(부분 수정 · 고침안)은 퇴고가 뒤따르지 않으므로 지금 글을 그대로 받는다.
- 다시 생성(`rewrite_episode`)과 서술 다듬기(`polish_episode`)는 `_write` 를 거쳐 `writer_system` 을 쓴다. 퇴고 단계를 켠 작품은 둘 다 나눈 규칙을 받는다.
- 퇴고 호출의 시스템은 지금처럼 `writer_system` 이다. 쓰기와 시스템 · `static_context` 가 같아 캐시가 맞는다.
- 퇴고 단계를 켜거나 끄면 그 작품의 시스템 프롬프트와 `static_context` 가 한 번 바뀐다. Claude 캐시 가족(`FAMILY_SYSTEM`)은 시스템 자리가 공통 글이라 그대로다. 사용자 메시지 앞의 원래 시스템 글이 바뀌어 그 작품의 캐시는 한 번 새로 쓴다.
- 자동 집필 추정(`autorun.estimate`)은 `writer_system(sim)` 과 `polish_prompt` 로 크기를 잰다. 고친 함수를 그대로 부르므로 따로 고치지 않는다. 위반 목록 크기만큼 늘어난다.

## 2. 규칙 층에 `polish` 더하기

- `schema.RuleLayerName = Literal["write", "plan", "polish"]`. `RuleLayer.layer` 설명에 'polish: 퇴고 요청의 작가 규칙' 을 더한다.
- `prompts.rule_layer` 는 퇴고 단계를 켜지 않은 작품에서 polish 줄을 write 로 돌려준다. 끈 작품에서 그 줄이 아무 요청에도 가지 않는 일을 막는다.
- `layer_rules(p, "polish")` 의 줄은 퇴고 요청의 '작가가 고른 퇴고 규칙' 블록에 지킬 것 · 피할 것으로 들어간다.
- 이 줄들은 작가가 쓴 자유 글이라 코드가 위반을 찾지 못한다. 그래서 '코드가 찾은 위반만' 원칙의 예외로, 위반 인용 없이 규칙으로만 넣는다.
- `pipeline.prune_rule_layers` 는 write 가 아닌 줄을 남기므로 고치지 않는다.
- 문체 화면(`static/style.js`): 칩이 집필 → 계획 → 퇴고 → 집필 차례로 돈다(`ruleLayer`). 퇴고는 퇴고 단계를 켠 작품에서만 차례에 든다.
- `RULE_LAYER_NAMES` 에 `polish: '퇴고'` 를 더하고, `RULE_LAYER_WHY` 에 '퇴고 칩은 쓴 뒤 퇴고할 때만 넣는 규칙이에요. 문장만 고쳐서 지킬 수 있는 규칙(표현 · 어휘 · 문장 모양)에 맞아요.' 를 더한다.
- 칩 색: `.chip.rl.polish` 를 더한다. 계획(`accent-soft`)과 다른 기존 토큰(`green-soft` · `green-ink`)을 쓴다. 새 색 토큰은 만들지 않는다. `app.css`, `docs/design/components/bundle.css`, `docs/design/components/Chip/README.md` 를 함께 고친다.
- 집필 규칙 수 표시(`writeRuleCount`, 20개 넘으면 표시)는 write 줄만 세므로 그대로다.

## 3. 퇴고 요청의 모양

### 3.1 차례

`static_context` → `# 다듬을 본문` → `POLISH_RULES`(지금 다섯 항목) → `# 작가가 고른 퇴고 규칙`(있을 때) → `# 찾은 자리`(있을 때, 맨 끝).

- 앞의 시스템과 `static_context` 는 쓰기 호출과 같다. 캐시 앞부분이 맞는다.
- 화마다 바뀌는 위반 목록은 맨 뒤다(Gemini 암묵 캐시는 앞 요청을 통째로 품어야 맞는다).
- 퇴고 단계를 켜지 않은 작품과 단편은 지금 `polish_prompt` 글 그대로다(프롬프트 스냅샷이 바뀌지 않는다).

### 3.2 찾은 자리 블록

```
# 찾은 자리 (코드가 이 본문에서 찾은 것. 이 문장들의 서술만 고칩니다. 대사 줄과 효과음 줄은 그대로 둡니다)
- [부정 후 재정의 · 한 화에 한 번까지] «그건 단순한 두려움이 아니었다.» «…»
- [감정 이름 서술 · 행동, 대사, 사물로] «안도감이 밀려왔다.»
- [금지 표현 '심장이 쿵'] «심장이 쿵 내려앉았다.»
- [되풀이 구절 · 103~105화에 그대로 나옴, 다른 말로] «창밖으로 형광등 불빛이 길게 늘어졌다.»
- [문장 끝] 서술 문장의 89%가 '~다.'로 끝납니다. 열에 일곱쯤으로 줄입니다. '~다.' 끝이 다섯 줄 넘게 이어진 곳 3군데: «…»
(대명사 9곳 가운데 6곳만 적었습니다)
```

- 한 줄은 `[규칙 이름 · 고칠 방향]` 과 인용 문장이다. 고칠 방향은 1절 표의 규칙 글에서 가져온다.
- 인용은 그 위반을 품은 서술 문장 하나를 120자까지 자른다.
- 대사 줄 · 효과음 줄(`pipeline.fixed_lines`)에 든 위반은 넣지 않는다. 그 줄은 `polish_problem` 가드가 바꾸지 못하게 막는다.
- 서식 흔적의 줄 머리 줄표는 효과음 줄이라 넣지 않는다(1.1 표 16번). 그대로 넣으면 퇴고가 가드를 깨고 다시 부르다 멈춘다.
- 문체 원문이 있는 작품은 기준값에서 원문이 원래 쓰는 만큼은 넣지 않는다. `style_baseline(p)` 의 `pattern_per_1k` 이상인 패턴은 뺀다(`metrics.drift` 와 같은 뜻).
- 상한: 규칙마다 인용 6개, 블록 전체 25줄. 넘으면 몇 곳 가운데 몇 곳을 적었는지 한 줄로 적는다(장편 예산 원칙).
- 찾는 함수는 한 곳에 둔다: `pipeline.polish_targets(p, n, text) -> list[PolishTarget]`(규칙 이름, 방향, 인용 목록, 전체 수). 프롬프트 글은 `prompts.polish_targets_block` 이 만든다.
- 문장 끝 덩어리의 자리를 돌려주는 함수(`metrics.da_runs`)를 더한다. 있는 지표 값은 바뀌지 않으므로 `METRICS_VERSION` 은 올리지 않는다.

### 3.3 지금 `POLISH_RULES` 와 합치기

- 다섯 항목(같은 순간 잇기, 관찰 보고 끝, '나는' 반복, 정리한 추론, 문장 끝 몫)은 그대로 둔다. 2026-11-04 실측의 이득이 이 항목에서 나왔다.
- 5번(문장 끝 몫)은 지금처럼 늘 넣는다. 찾은 자리의 '[문장 끝]' 줄은 그 화가 몫을 넘었을 때 숫자와 자리를 더한다.
- '지킬 것' 의 셋째 줄('스타일 프로필의 문단 규칙과 어휘 규칙은 그대로 따릅니다')은 그대로다.

### 3.4 위반이 없을 때

- 추천: 호출을 건너뛰지 않는다. 찾은 자리 블록만 빠진다.
- 까닭: 다섯 항목은 위반 목록과 상관없이 적용되고, 실측 이득이 거기서 나왔다.
- 퇴고 기록(`sent` 의 polish 기록)에 찾은 자리 수와 퇴고 뒤 다시 센 수를 남긴다. 화면의 '찾은 자리 n곳'이 이 값을 쓴다.

### 3.5 가드

- `polish_problem`(대사 · 효과음 줄 불변, 분량 0.85~1.15배)과 `polish_tics` 는 그대로다.
- 퇴고 뒤 찾은 자리가 늘면 경고만 남긴다. 다시 부르지 않는다(호출 수를 늘리지 않는다). 실험에서 늘어난 판이 잦으면 다시 정한다.

- 질문: 금지 규칙을 뺀 집필에 표적 퇴고를 붙인 판이 지금 판보다 나쁘지 않은가.

## 5.1 실험 결과 (2026-11-10 ~ 11)

결과 글은 `reports/polish-stage-2026-11-10/report.md`(커밋하지 않음).

## 5.2 구현이 초안과 달라진 곳

- 찾는 함수는 `pipeline` 이 아니라 새 모듈 `canon/polishscan.py` 에 두었다. `prompts.polish_prompt` 가 부르므로 `pipeline` 을 들이지 않으려는 것이다.
- 찾은 자리 수를 `sent` 기록에 남기지 않았다. 판 비교는 `GET …/polish-targets` 가 그때 센다(지금 본문 · 새 판).
- 다시 생성을 퇴고한 경우 퇴고 전 새 판은 `versions` 에 두지 않는다. 퇴고가 멈추면 퇴고 전 새 판을 후보로 둔다.
- revise 모델이 Gemini 인지 보는 안내는 만들지 않았다. '쓴 뒤 퇴고' 설명 글이 늘 Claude 실측을 적는다.
- 퇴고 단계 스위치는 '지킬 · 피할 것' 카드 머리의 '쓴 뒤 퇴고' 버튼이다. 문체 화면 저장과 함께 저장된다.

| `canon/mock.py` | 퇴고 응답이 찾은 자리를 고친 모양을 낸다 |
| `canon/static/style.js` · `app.css` | 층 칩 셋, 퇴고 단계 켜기 |
| `canon/static/write.js` · `rewrite.js` · `auto.js` | 판 비교의 찾은 자리 목록, 자동 집필 잠금 안내 |

- LLM 호출 경로는 새로 생기지 않는다. 퇴고는 지금처럼 revise 단계(`get_llm("revise")`)다.
- 대화 에이전트(`agent.py`)는 `polish_stage` 와 `rule_layers` 를 고치지 않는다(작가가 고르는 설정).

## 데이터 · 스키마

- `Settings.polish_stage: bool = False`. 켜면 장편의 집필 요청에서 1절의 퇴고 줄을 빼고, 퇴고 요청에 찾은 자리를 넣는다. 단편은 켜도 따르지 않는다.
- `RuleLayerName` 에 `"polish"`.
- `sent` 의 polish 기록에 찾은 자리 수(퇴고 전 · 뒤)를 더한다. 프로그램만 채우는 칸이다.
- 옛 `project.json` 은 기본값으로 지금과 같이 읽힌다.
- LLM 이 채우는 스키마는 바뀌지 않는다.

## 규칙

- 승인 흐름: 퇴고 판은 손 집필에서 새 판 후보로 오고, 작가가 집필 화면에서 고른다.
- 자동 집필은 지금 `_polish` 그대로 퇴고 판을 본문으로 넣고 쓴 판은 이전 판에 남긴다.
- 작가가 쓴 `written` 화는 자동 집필이 퇴고하지 않는다(지금 규칙).
- 퇴고는 인물 설정 · 상태 · 관계를 바꾸지 않는다. 본문 판만 만든다.
- 되돌리기: 퇴고 전 판은 `versions` 에 남는다(지금 `replace_text` · `set_candidate`).

## 화면 · 명령줄 · 프롬프트

- 퇴고 단계 켜기 스위치는 문체 화면 '지킬 · 피할 것' 카드 머리에 둔다(장편만). 문구: '쓴 뒤 퇴고' / '하지 말 것은 집필 요청에서 빼고, 쓴 뒤 퇴고 판에서 고쳐요. 화마다 AI 호출이 하나 늘어요.'
- 고친 뒤 `brief` 출력(작업지시서)을 켠 작품 · 끈 작품 둘 다 본다.
- 명령줄: `write` 에 따로 옵션을 더하지 않는다. 퇴고 단계를 켠 작품은 `write` 가 쓴 뒤 퇴고 판을 새 판 후보로 둔다고 안내한다(정할 것 1을 따르면).
